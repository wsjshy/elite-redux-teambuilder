## 三、审计报告 §9 未决项补齐

### U-3：jsDelivr CDN 对 `@gh-pages` 分支引用的缓存 TTL —— **已实测闭环**

**被测 URL**（从钉住 index.html 的 `__ER_LOADER_FB__` 兜底块原样提取）：
`https://gcore.jsdelivr.net/gh/wsjshy/elite-redux-teambuilder@gh-pages/data_lite_v498.js?v=v498`
（兜底块只在同域加载失败时触发，拉三个分片 `data_lite_v498.js` / `data_species_v498.js` / `data_adv_v498.js`，均带 `?v=v498`。）

**实测响应头（2026-11-07 16:32 GMT，HEAD 实测，非估算）**：
```
Cache-Control: public, max-age=604800, s-maxage=43200
x-jsd-version: gh-pages
x-jsd-version-type: branch
ETag: W/"5cb1f-784c63a9109afc95"
Age: 0
X-Cache: HIT, MISS        ← jsDelivr Gcore 层
cf-cache-status: MISS     ← Cloudflare 层
Vary: Accept-Encoding
```

逐条回答：
1. **TTL 到底多少**：`s-maxage=43200` = **共享 CDN 边缘缓存 12 小时**；`max-age=604800` = **浏览器本地缓存 7 天**。`x-jsd-version-type: branch` 证实这是分支引用的响应策略。
2. **`?v=v498` 能否绕开**：查询串是缓存键的一部分（响应头 `Vary` 只有 `Accept-Encoding`，不按查询串变化——即不同查询串各自成一条缓存，互不顶替）。改查询串等于开一条新缓存键、强制回源取最新分支解析；但**不会清除旧缓存键**，也不影响别人已缓存的旧条目。对本项目：分片文件名本身已含 v498 且内容随部署不变，这个参数只是防陈旧，无副作用。
3. **force-push 后旧缓存多久失效**：边缘层 **≤12 小时**（s-maxage 到期后回源重新解析 `@gh-pages` 指向的新 commit）；浏览器层最久 **7 天**（除非用户强刷或查询串变化）。jsDelivr 对 GitHub 分支引用无 npm 那种「发版即自动 purge」机制（响应头无任何 purge/过期加速信号）。
4. **对「部署后旧 index.html 仍引用已删文件」这个风险意味着什么**：**量化结论 = 风险≈0**。因为 jsDelivr 兜底块只拉 3 个**当前仍在线的运行时分片**，从不引用那 116 个历史快照；真正会因删除而 404 的是「外部直链书签」（见 U-4），与 jsDelivr 缓存窗口无关。唯一残留影响：浏览器里已缓存的旧分片最长 7 天内不会自动更新——但旧分片对应旧页面，数据自洽，无害。

> 来源说明：官方文档页 https://www.jsdelivr.com/documentation 为 JS 渲染，web.fetch 抓不到正文段落；以上结论以**对本项目真实 URL 的实测响应头**为准（比文档更贴近实际）。如后续需书面依据，可在浏览器打开文档站手动核对 Caching 一节。
