# ER 通用机制与招式/特性源码口径（2026-11-08）

> 本文回答一个问题：**玩家在 2.65 里实际感受到的规则，源码里到底是怎么写的**。
> 所有结论都标了源码位置，可以自己回查；查不到的就写「查不到」，不猜。

## 〇、先定口径：两个分支不是一回事

| 分支 | 最后提交 | 特性定义数 | 用途 |
|---|---|---|---|
| `master` | **2025-06-04** | **618 条**（`#define`，id 0–617） | **旧分支**，只能解释一年前那版 |
| `upcoming` | **2026-11-07** | **1073 个 `Impl<ABILITY_>` 名字** | **当前分支**，与游戏内 1034 个特性对得上 |

**这一节最初写反了，已更正。** 初稿把 `master` 当成「2.65 发行版对应代码」，
理由是它保留着 C 版 `battle_util.c`（694 KB）而 upcoming 只剩 441 KB。但真正的判据是**特性数量**：

- 游戏数据层 `ERDATA.abilities` 有 **1034 条**（id 0–1033，连续无缺口）；
- `master` 的 `include/constants/abilities.h` 只有 **618 条** `#define`，
  末条 `ABILITY_ROCKHARD_WILL 617`，`ABILITIES_COUNT_CUSTOM = ABILITY_ROCKHARD_WILL + 1` = **618**；
- `#733 拳舞`、`#788 冰川暴怒` 这类 id **在 master 里根本没有定义**（超出 617），
  只在 upcoming 的 `src/abilities.cc` 里存在。

**618 对 1034，缺 416 个特性 —— master 不可能是玩家在玩的这一版。**

### 0.1 那 416 个 id 怎么查

upcoming 把常量头文件改成了**生成式**（仓库里有 `.github/workflows/regenerate-ability-files.yml`），
`include/constants/abilities.h` 在 upcoming 的树里**整个文件不存在**，所以**没法按 id 查**。
替代路径是**按英文名对**：

| 项 | 数量 |
|---|---|
| 游戏特性总数 | 1034 |
| master 已定义（id 0–617） | 618 |
| 超出 master 的 | 416 |
| 其中能在 upcoming 按英文名匹配到 `Impl<ABILITY_>` | **397（95.4%）** |
| 两个分支都没有 | 19 |

那 19 条（如 `#628 Pretty Privilege`、`#629 Shallow Grave`、`#642 Jackhammer`）
在 master 和 upcoming 里都搜不到常量，属于**源码无法判定**，只能按数据层文案记录。

### 0.2 直接后果：163/164 的结论原来写错了

`ABILITY_TURBOBLAZE`（163 涡轮火焰）/ `ABILITY_TERAVOLT`（164 兆级电压）的「加属性」——
初版写「`AddBattlerType` 在 master 全仓 0 命中 → 2.65 里没有生效，是下一版预留」。
**这个推理把旧分支当成当前分支，结论是错的。**

upcoming 的 `src/abilities.cc:2256`：

```cpp
constexpr Ability Impl<ABILITY_TURBOBLAZE> = {
    .onEntry = +[](ON_ENTRY) -> int { return AddBattlerType(battler, TYPE_FIRE); },
    .onMoldBreaker = Impl<ABILITY_MOLD_BREAKER>.onMoldBreaker,
    .addsType = TYPE_FIRE,
};
```

`AddBattlerType`（`src/abilities.cc:227`）的实现是：

```cpp
static int AddBattlerType(u8 battler, Type type) {
    CHECK_NOT(IS_BATTLER_OF_TYPE(battler, type))   // 本来就是这个属性 → 不加
    gBattleMons[battler].type3 = type;             // 写进第三属性槽
    BattleScriptPushCursorAndCallback(BattleScript_BattlerAddedTheType);
    return TRUE;
}
```

**「加属性」= 写入 `type3`，是叠加出第三个属性，不是替换。** 并且本来就是该属性时不触发。

**方法论教训（已升级为红线）**：判断「源码里有没有」之前，先确认**这个分支对应哪个版本**。
用提交日期 + 数据层条目数两个独立指标交叉，比凭"哪个文件大"猜可靠得多。

## 一、伤害是怎么算出来的

源码：`src/battle_util.c:15056` `DoMoveDamageCalcInternal`

```
① 相性为 0 → 直接 return -1（打不动，连伤害数字都不算）
② power = CalcMoveBasePowerAfterModifiers(...)     ← 特性/道具/天气改威力都在这一步
③ dmg  = ((攻击方等级 * 2) / 5) + 2
④ dmg *= power
⑤ dmg *= CalcAttackStat(...)
⑥ dmg /= CalcDefenseStat(...)
⑦ dmg  = (dmg / 50) + 2
⑧ dmg  = CalcFinalDmg(...)                          ← 相性倍率、会心、随机数、道具、特性
⑨ Monotype Champ 修正（见第六节）
```

这是标准的 Gen3 公式骨架，②⑥⑤⑧ 是 ER 塞特性的地方。**排查「为什么这一下伤害不对」时，按 ①→⑨ 顺序找断点，比凭描述猜快得多。**

## 二、属性相性：ER 把它当「可改写量」

源码：`src/battle_util.c:15186` `MulByTypeEffectiveness`

正统作品里相性是死表。ER 把它做成**可被特性拦截并重写**的量，这就是为什么很多"本该免疫"的组合在 ER 里打得动。

### 2.1 特性改写（源码里逐个 `else if` 分支）

| 特性 | id | 触发条件（源码原文） | 相性被改成 |
|---|---|---|---|
| 一般皮肤 Normalize | 96 | 一般属性招式且原相性 ≠ 0 | **1.0**（无视抗性，见数据层"无视抗性"） |
| 胆量 Scrappy | 113 | 格斗/一般 → 幽灵 | 0 → **1.0** |
| 幻痛 Phantom Pain | 457 | 幽灵 → 一般 | 0 → **1.0** |
| 地面冲击 Ground Shock | 285 | 电 → 地面，且原相性为 0 | 0 → **0.5**（不是 1.0，是**抵抗**） |
| 电力过载 Overcharge | 349 | 电 → 电 | → **2.0**（效果绝佳） |
| 熔岩 Molten Down | 357 | 火 → 岩石 | → **2.0** |
| 岩浆吞噬者 Magma Eater | 467 | 火 → 岩石 | → **2.0** |
| 腐蚀 Corrosion | 212 | 毒 → 钢 | 0 → **2.0** |

**最容易算错的是「地面冲击」**：它写的是 `mod = 0.5`，也就是电属性招式打地面系**从免疫变成抵抗**，不是变成正常伤害。数据层写「改为抵抗」是对的，但玩家常按"能打"理解成 1 倍。

### 2.2 全局规则（不属于任何特性，人人都会遇到）

同一函数里，这几条**没有** `BATTLER_HAS_ABILITY` 前缀，属于通用修正：

| 条件 | 结果 | 源码 |
|---|---|---|
| `EFFECT_SLUDGE` 打水属性 | 2.0 | L15297 |
| `EFFECT_POISON_GAS` 打飞行属性 | 2.0 | L15299 |
| `MOVE_GIGATON_HAMMER` 打钢属性 | 2.0 | L15301 |
| 地面 → 飞行，**且目标已接地** | 0 → 1.0 | L15303 |
| 火 → 目标带 `tarShot` | 2.0 | L15305 |
| **强风天气（`WEATHER_STRONG_WINDS`）下，飞行系受到的 ≥2.0 相性** | **强制压回 1.0** | L15309-15313 |

最后一条最隐蔽：**强风一开，飞行系的弱点全部消失**。这是天气机制，不是特性，配招时不会有人提醒你。

## 三、能力等级倍率：标准 Gen3，没有魔改

源码：`src/pokemon.c:3545` `gStatStageRatios[MAX_STAT_STAGE + 1][2]`

```
-6: 10/40   -5: 10/35   -4: 10/30   -3: 10/25   -2: 10/20   -1: 10/15
 0: 10/10
+1: 15/10   +2: 20/10   +3: 25/10   +4: 30/10   +5: 35/10   +6: 40/10
```

即 ±1 为 1.5 倍 / 0.67 倍，±2 为 2 倍 / 0.5 倍，±6 为 4 倍 / 0.25 倍，**与官方一致**。
所以"能力等级被我算错了"这类问题，基本可以排除——除非涉及特性对**倍率本身**的改写（那是另一套逻辑，不在这个表里）。

## 四、招式效果：993 个 `EFFECT_`，不靠名字猜

- 招式数据：`src/data/battle_moves.h`（366,858 B，993 处 `EFFECT_` 引用）
- 效果实现：`src/battle_script_commands.c` 里 `case EFFECT_XXX:` 分支 + `data/battle_scripts_1.s` 汇编脚本

**结论：招式行为由 `EFFECT_` 分派，名字和描述只是标签。**
同一个 `EFFECT_` 可以挂很多招式（例如各种「附加异常状态」的招式共用一套代码，只有概率字段不同）。
因此**不要用招式名去推效果**，要查它挂的是哪个 `EFFECT_`，再去看那个 `EFFECT_` 的 case。

## 五、天气：ER 取消了传统的水/火属性天气加成

**这是最容易被正统作品经验误导的一条。**

正统 Gen3 及之后：晴天火系招式 ×1.5，雨天水系招式 ×1.5。**ER 里这两条都不存在。**

**证据**：在 `src/battle_util.c`（694,131 B 全文）、`src/battle_script_commands.c`、`src/battle_main.c`
里同时搜 `WEATHER_SUN_ANY` / `WEATHER_RAIN` 与 `UQ_4_12(1.5)` 或 `1.5`，
**命中数 0**。基础威力函数 `CalcMoveBasePowerAfterModifiers`（`src/battle_util.c:12838`）
从头到尾没有针对 `moveType` 的天气倍率分支。

**ER 里的天气只剩这些作用**：

| 类型 | 位置 | 实际作用 |
|---|---|---|
| 冰雹 `WEATHER_HAIL_ANY` | `battle_util.c:13983` | 特性 Whiteout 冰系招式 ×1.5（**靠特性，不是天气本身**） |
| 冰雹 | `battle_util.c:13317` | 特性 Christmas Spirit 使受到的伤害 ×0.5 |
| 沙暴 `WEATHER_SANDSTORM_ANY` | `battle_util.c:13324` | 特性 Dune Terror 使受到的伤害 ×0.65 |
| 强风 `WEATHER_STRONG_WINDS` | `battle_util.c:15309` | 飞行系受到的 ≥2.0 相性强制压回 1.0（**弱点全消失**） |
| 任意天气 | `battle_util.c:12638` | 气象球改属性与威力 |
| — | `battle_util.c:14730~14757` | `EFFECT_WEATHER_BOOST` 类招式按天气改威力 |

**配招含义**：不要为了"雨天水系加成"去堆水招，也不要指望晴天火系增伤。天气在 ER 里的价值集中在
① 场地/天气特效本身（如沙暴每回合削血）② 触发特定特性 ③ 让气象球/天气球系招式变强。

## 六、Monotype Champ：ER 自己加的一套修正

源码：`DoMoveDamageCalcInternal` 末尾 `switch (getMonotypeChampType())`

这是 ER 独有的，正统作品没有对应机制：

| Champ 类型 | 修正 |
|---|---|
| 草 / 超 / 电 / 毒 / 钢 | 对手不是玩家方 → 伤害 **减半** |
| 地面 / 格斗 | 对手不是玩家方，且相性 ≥ 2.0 → **减半** |
| 格斗 | 玩家防守、对方用格斗招式打过来 → **×2** |
| 冰 | 玩家防守、对方攻击 → **×2** |

换句话说，这四类 Champ 是**针对玩家方的难度调节**：前几类让对面打你更轻，格斗/冰反而让对面打你更重。

## 七、全量特性普查结论（游戏内 1034 条，旧分支仅覆盖 618）

方法：用 `include/constants/abilities.h` 的 `#define ABILITY_XXX <id>` 做 **id → 常量名**映射，再在 master 全仓 grep 每个常量。

> **为什么必须走 id**：数据层的英文名是压缩过的（`WandrngSprit`、`CuriusMedicn`、`Twist. Dimension`），由英文名推不出常量名。第一版按英文名推得 441 条「零命中」，全是假阴性。

### 6.1 覆盖率

| 项 | 数值 |
|---|---|
| 数据层特性条目（有 id） | 618 |
| 在源码中有引用 | **618 / 618** |
| 在「效果实现文件」中有引用 | **616** |
| 仅出现在 AI 判断 | **1**（#180 共生 Symbiosis） |
| 仅出现在声明与文本 | **1**（#600 龙族拳手 Brawling Wyvern） |

「效果实现文件」= `src/battle_util.c`、`src/battle_script_commands.c`、`data/battle_scripts_1.s`/`_2.s`、`src/battle_main.c`、`src/pokemon.c`。

### 6.2 复杂度分布

`src/battle_util.c` 内命中次数：min 0 / p25 1 / **p50 2** / p75 3 / max 17。

中位数只有 2，说明**绝大多数特性是「表驱动」或「单点判定」**，不是每条都有一段可叙述的复杂机制。
最多的几条：`#197 界限盾壳`、`#563 发号施令`（各 17），`#59 阴晴不定`（13），`#122 花之礼`（12），`#90 毒疗`（12）。

### 6.3 「读代码行自动生成效果摘要」这条路走不通

618 条里，只有 **34 条**的关键行带 `//` 注释（唯一可直接读出的语义来源），且集中在 `battle_ai_util.c`(273 行)、`battle_util.c`(203 行)。

反例：`#262 电晶体` 数据写「电属性招式威力提升至 1.5 倍」，但它在效果文件里只有 1 处引用、且那行不含任何数字——真正的倍率写在通用表里，单看常量的出现位置读不出效果。

**所以全量覆盖的正确形态是「覆盖率台账 + 少数高价值条目手工详解」，不是给 618 条各编一段散文。**

## 十、招式机制归类：950 招背后只有 402 个 `EFFECT_`

**招式行为不是由名字决定的，是由 `effect` 字段分派的。** 名字和描述只是标签。
所以判断一个新招"到底干什么"，第一步永远是看它的 `EFFECT_`。

- 950 个招式 → **402 个 distinct `EFFECT_`**
- 其中 **280 个 `EFFECT` 只挂 1 个招式**（专属实现，基本是作者为单个招写的脚本）
- 剩下 122 个 `EFFECT` 承担 670 个招式

**同一 `EFFECT_` 下的招式，附加机制完全一致，只是属性/威力/命中不同。** 这条对配招很有用：
想知道某招的附加效果，直接看它的同组兄弟就行。

## 十一、`#513 小马之力`：描述写「锐利+神秘」，实际全招都吃 1.3 倍

`#513 ABILITY_PONY_POWER`，数据层描述只有四个字：**「锐利之刃+神秘之刃」**。
源码注释也写着 `// Combines Keen Edge & Mystic Blades.`。

按这个描述，玩家会以为它等价于「锐利之刃」或「神秘之刃」，即**只对锐利类招式加成**。实际不是。

`src/battle_util.c` 基础威力函数里的原文：

```c
// Mystic Blades
if(BATTLER_HAS_ABILITY(battlerAtk, ABILITY_PONY_POWER)){
    if (gBattleMoves[move].flags & FLAG_KEEN_EDGE_BOOST)
         MulModifier(&modifier, UQ_4_12(1.3));
         MulModifier(&modifier, UQ_4_12(1.3));   // ← 缩进在 if 内，语义在 if 外
}
```

**第二个 `MulModifier` 虽然缩进对齐到了 `if` 里面，但没有花括号，C 的语义是「`if` 只控制紧随的第一条语句」**，
所以第二行**无条件执行**。真实效果：

| 招式类型 | 实际倍率 |
|---|---|
| 锐利类（`FLAG_KEEN_EDGE_BOOST`） | 1.3 × 1.3 = **×1.69** |
| **其他所有招式** | 第二条单独生效 = **×1.3** |

**对照**：`ABILITY_KEEN_EDGE`（锐利之刃）和 `ABILITY_MYSTIC_BLADES`（神秘之刃）都只在锐利类招式上 ×1.3。
也就是说 **`#513` 比它号称「合并」的那两个特性强得多，因为它给全部招式都发了 1.3 倍**。

**判断口径**：这是一处漏花括号的代码瑕疵（大概率本想两条都在 `if` 内、做 1.69 的锐利加成，
结果第二条落到 `if` 外成了全招加成）。但**无论作者意图是什么，2.65 里的实际行为就是上表**。

**玩家含义**：看到「小马之力」不要按「锐利之刃」理解，它是一条**通用增伤 30%** 的特性，
配招时不需要专门堆锐利类招式去吃加成。

## 十二、破格穿透：白名单表已被废弃，改成特性自带 `breakable` 标志

**这是旧分支口径失效最彻底的一处。** 旧版（master, 2025-06）用一张中心表
`sAbilitiesAffectedByMoldBreaker`，108 条；当前分支（upcoming, 2026-11）**这张表整个不存在**
（全仓 0 命中），改成每个特性在自己的 `Impl<>` 里声明 `.breakable = TRUE`。

### 12.1 判定函数

`src/battle_util.c:9369`：

```c
int IsSuppressed(int battler, AbilityEnum ability, int checkMoldBreaker) {
    if ((checkMoldBreaker && battler != gBattlerAttacker && gHitMarker & HITMARKER_MOLD_BREAKER
         && gAbilities[ability].breakable) ||
        (((gFieldTimers.neutralizingGas && (B_NEUTRALIZING_GAS_WORKS_ON_INNATES || GetBattlerAbility(battler) == ability))
          || gStatuses3[battler] & STATUS3_GASTRO_ACID) && !IsUnsuppressableAbility(ability))) {
        return !DoesBattlerHaveAbilityShield(battler);
    }
    return FALSE;
}
```

**破格要穿透，四个条件缺一不可**：

1. `checkMoldBreaker` —— 调用方主动要求检查（不是所有判定都检查）；
2. `battler != gBattlerAttacker` —— **只有出招方穿透防守方**，反过来不行；
3. `gHitMarker & HITMARKER_MOLD_BREAKER` —— 本回合命中标记里带破格；
4. `gAbilities[ability].breakable` —— 目标那个特性**自己声明了可被破**。

### 12.2 规模：207，不是 108

统计 `src/abilities.cc` 里 1071 个 `Impl<>` 块：

| 项 | 数量 |
|---|---|
| `Impl<>` 块总数 | 1071 |
| 含 `.breakable` 声明 | **207**（全部为 `TRUE`，无一例 `FALSE`） |
| 旧分支白名单 | 108（已作废） |

**「破格只穿 1/6」这个说法在当前版本不成立** —— 207 / 1034 ≈ 20%，比旧版几乎翻倍。

### 12.3 一条对配招有用的边界：特性护盾能挡

`return !DoesBattlerHaveAbilityShield(battler);`
—— 目标持有道具 **Ability Shield（特性护盾）** 时，破格直接穿不进去。
这是打「破格队」时唯一一个不依赖特性、纯靠道具的反制手段。

### 12.4 不可被破的

破格三兄弟自己（`MOLD_BREAKER` / `TURBOBLAZE` / `TERAVOLT`）在 `abilities.cc` 里用的是
`.onMoldBreaker`（声明「我是破格系」），**不是** `.breakable`（声明「我可被破」），
所以它们本身穿不进彼此。同类的还有 `BLIND_RAGE`、`OVERRULE`。

### 12.5 落页面

`index.html` 的 `ABI_DETAIL['104']`（破格）已整块重写为 6 行：
判定条件 / 穿透得到 / 穿透不到 / 会被挡下 / 会失效 / 先天槽同样穿透。
163、164 的「穿透范围」行同步改成「207 个 breakable」，探针 D3/D4 断言一并改为 `breakable` + `207`。

## 十三、Hell 难度会把相性倍率改掉（这一层以前完全没写）

`src/pokemon.c:6377`：

```c
bool8 isHellMode(void) { return (gSaveBlock2Ptr->gameDifficulty == DIFFICULTY_HELL); }
```

**Hell 难度是玩家在游戏里自己选的难度档**（`gameDifficulty`），不是某个特性或道具。

### 13.1 相性倍率被压平

`src/battle_util.c:8038`：

```c
// Super-effective damage is reduced from 2x to 1.5x, and 4x to 2x
if (isHellMode() && HELL_MODE_TYPE_EFFECTIVENESS_CHANGE) {
    switch (modifier) {
        case UQ_4_12(2.0):  modifier = UQ_4_12(1.5); break;
        case UQ_4_12(4.0):  modifier = UQ_4_12(2.5); break;
    }

```

| 相性 | 标准难度 | Hell 难度 |
|---|---|---|
| 效果绝佳 2× | 2.0 | **1.5** |
| 双重效果绝佳 4× | 4.0 | **2.5** |

**⚠ 注释和代码不一致**：注释写「4x to 2x」，代码实际是 **2.5**。按代码为准。

这条对配招影响很大：**Hell 难度下「打出效果绝佳」的收益从 100% 降到 50%**，
堆相性收益不如标准难度那么划算；反过来，硬吃一发效果绝佳也没那么痛。

### 14.4 接进工具计算（v4.193）：这批特性是「攻击方」的，不是防守方的

**这是本轮最容易搞反的一点，记下来。**

`src/battle_util.c:7947` 的签名是：

```c
ON_ABILITY(battlerAtk, FALSE, gAbilities[ability].onTypeEffectiveness, ...)
```

`ON_ABILITY` 的第一个参数是**遍历谁的特性**（`GetBattlerAbilityInSlot(battler, idx)`）。
这里传的是 `battlerAtk` —— **攻击方**。

所以「地面冲击」「腐蚀」「胆量」这类特性的真实语义是：

> **我自己出招时**，我的电招打地面不再无效（0 → 0.5）、我的毒招能打钢（0 → 2.0）、
> 我的普通招能打幽灵（0 → 1.0）。

**不是**「别人打我时我怎么样」。我第一版把它接进了防守口径函数 `defCellTrio`，
意思变成了「带地面冲击的宝可梦被电打只吃 0.5」——**完全反了，已回滚。**

### 16.3 顺带发现的真实缺陷：`matchup` 索引方向

`ERDATA.matchup` 的布局是 **`[防守属性][攻击属性]`**。实测：

```
matchup[地面][电] = 0     ← 电打地面无效
matchup[电][地面] = 2     ← 地面打电克制
matchup[钢][毒]   = 0     ← 毒打钢无效
matchup[毒][钢]   = 1
```

而上述三处（盲点计算 / `canHitSuper` / 核心盲点排序）写的是 `matchup[攻击][防守]`，
**方向反了** —— 算出来的是「目标属性招式打自己」。

v4.196 统一改走 `coverMultOf(s, atkTy, defTy)`，方向一并修正。

### 16.4 新增的统一求值口

```js
function coverMultOf(s,atkTy,defTy){
  var ai=tIdx(atkTy),di=tIdx(defTy);
  if(ai<0||di<0)return 1;
  /* ERDATA.matchup 是 [防守属性][攻击属性] —— 先防守再攻击，别写反 */
  var v=ERDATA.matchup[di][ai];
  var c=(v===0?0:((v===0.5||v===3)?0.5:(v===2?2:1)));
  var abn=(s&&s.inns)?s.inns:[];
  if(!abn.length)return c;
  var selfT=[];
  if(s.t1&&s.t1!=='-')selfT.push(s.t1);
  if(s.t2&&s.t2!=='-')selfT.push(s.t2);
  for(var q=0;q<abn.length;q++){c=abiTeApplyOne(abn[q],atkTy,defTy,c,selfT);}
  return c;
}
```

**约定：凡是「某只宝可梦的某属性招式打某属性」，一律走 `coverMultOf`，
不要再直接查 `ERDATA.matchup`。** 纯属性维度的表照旧直查。

### 16.5 踩坑记录：插入位置插进了函数体内

第一次插入 `coverMultOf` 时，用「找 `function abiTeApplyOne(` → 找下一个 `strip()=='}'`」
定位结尾，结果那个 `}` 是 **`for` 循环的右括号**，不是函数结尾 →
`coverMultOf` 被塞进了 `abiTeApplyOne` 函数体内部，probe 全崩
（`ReferenceError: coverMultOf is not defined`，连带 32 项 FAIL）。

**正确做法**：用「函数结尾的语义特征行」定位，`abiTeApplyOne` 的结尾是
`'  return out;'` 且下一行 `'}'` —— 两个条件同时成立才算函数结束。

### 17.4 工具里怎么区分「相性」和「减伤」

**两者必须分开显示。**相性只有 0 / 0.5 / 1 / 2 四个值，是属性表决定的；
减伤倍率是特性自带的伤害修正，和属性表无关。

`abiDesc` 里加了一块：

- **「受到伤害倍率」** —— 取自 `ABI_DMG_MOD` / `ABI_DMG_ALL`，
  明确注明「与属性相的 0.5× / 2× 不是一回事」
- 文案按倍率自动分流：`<0.5` 标「强减伤」，`<1` 标「减伤」，`>1` 标「增伤，是弱点」

**`defCellTrio` 不接减伤倍率** —— 它返回的是相性值，
塞 ×0.7 进去会破坏「0.5 的整数倍」这个语义。

### 17.5 解析踩坑

1. **把 `.onOffensiveMultiplier` 段也抓进来了** —— `FOSSILIZED` 看似「岩石 ×0.5 又 ×1.2」矛盾，
   实际前者是 `.onDefensiveMultiplier`（挨打减半），后者是 `.onOffensiveMultiplier`
   （自己打岩石招加伤）。**只解析 `.onDefensiveMultiplier` 段才对。**

   全归成了「无条件全伤害」。
3. **if/else 分段被当成两条独立规则** —— `BARK_SKIN` / `FEATHERCOAT` 的

## 十八、界面可读性整改（v4.198）

用户反馈「字体感觉太小了，重点也不明确」。查下来是两个问题叠在一起。

### 18.1 字号：基础 14px，但子元素全降到 10-12px

全项目硬编码字号统计（改前）：

| 字号 | 出现次数 |
|---|---|
| 8px | 1 |
| 9px | 3 |
| 10px | **57** |
| 11px | **168** |
| 12px | **110** |
| 13px | 49 |
| 14px | 15 |

`body` 是 14px，但真正铺满屏幕的标签、注释、表格全在 10-12px，
所以整体观感就是「小」。无 `font:` 简写，可以安全批量处理。

**抬升方案（保住层级，不能压平）：**

| 原 | 新 | 用途 |
|---|---|---|
| 8 / 9px | 11px | 极小注释 |
| 10px | 12px | 标签 |
| 11px | 12.5px | 辅助正文 |
| 12px | 13.5px | 正文 |
| 13px | 14px | 表格主体 |
| 14px | 15px | 小标题 / body |
| 15px | 16.5px | 标题 |
| 16px | 17.5px | 大标题 |
| 17px | 18px | — |
| 20px | 22px | — |

**关键技术点：用占位符分批替换。**
直接顺序替换会连锁 —— 先 `12.5→13`，再 `12→13`，刚生成的 12.5 会被
下一条规则再吃掉，最后全部塌成同一级，反而**比改之前更不分明**。
第一版就是这么错的，全部变成 13px 后回退重做。

正确做法：每个原值先换成唯一占位 `\x00FS{i}\x00`，全部打完标记再统一还原。

### 18.2 重点不明确：物种名和提示语一样重

卡片里 `.nm`（物种名）13.5px、`.mini`（点击提示）13.5px —— **完全同级**，
所以扫一眼分不出主次。种族值那行 `.bs` 反而 14px / 600 更重。

|---|---|---|
| `.nm` 物种名 | 13.5px / 600 | **17px / 700** |
| `.en` 英文名 | 12.5px | **11.5px / opacity .7**（退为背景） |
| `.bs` 种族值行 | 14px / 600 / 主色 | **12.5px / 400 / 次色**（降级） |
| 种族值**数字** | 混在文字里 | **单独 16px / 主色 / 左距 4px** |
| `.mini` 提示语 | 13.5px | **12px / opacity .75** |

即：**把视觉重量从「标签行」转移到「物种名 + 关键数字」**。

### 18.3 顺带修掉：唯一特性被渲染成「1 选 1」

### 18.4 顺带修掉：招式反查是空表

截图走查时发现「招式反查」tab 只有表头、`mvTable` 高度 28px、11 个元素。

**根因**：`ERDATA.moves` 在 `data_adv_v498.js` 这个**异步分片**里，

分片加载器本身有事件（`er-shard-adv` / `er-ready`），补监听即可：

```js
try{['er-shard-adv','er-ready'].forEach(function(ev){
  document.addEventListener(ev,function(){try{renderMv()}catch(e){}});
});}catch(e){}
```

修完实测 1032 条全部渲染（`rows` 从 425 分位表行 → 1457）。

**这类 bug 的特征是「DOM 空、无报错、门禁全绿」** —— smoke 和 probe 都抓不到，
只能靠真实渲染走查。所以本轮补了 CDP 截图工具（`%TEMP%\cdp_shot.py`），
用 `--remote-debugging-port` + `Page.captureScreenshot` 逐 tab 截图验证。

### 18.5 教训

### 18.6 v4.199 补齐：A 表漏装 + C 类 32 条条件型上线

走查时对账发现两处缺口。

**缺口一：A 表少了 3 条增伤。**
脚本跑出 A 类 18 条，但页面表里只有 15 条。少的是
`毛茸茸`（火 ×2.0）`极致蓬松`（火 ×2.0）`液化`（水 ×2.0）—— 都是**增伤**，
带这种特性反而吃双倍。落地时被当成「减伤表」过滤掉了。

**但进一步核对源码后发现不能简单补进 A 表：**

```
L3007| if (moveType == TYPE_FIRE) MUL(2.0);            ← 火招式 ×2
L3008| if (IsMoveMakingContact(move, attacker)) MUL(.5); ← 接触招式 ×0.5
```

同一个 `.onDefensiveMultiplier` 段里**两条规则**（行号连续）。
按既定判据「段内多于 1 条 ⇒ 整体归 C」，这三个特性应当整体归 C，
把两条规则都写出来，而不是把 ×2.0 那条塞进 A 表。

所以最终形态是：**A 表保持 15 条不动，这三条进入 C 表，两条规则并列展示。**

**缺口二：C 类 32 条此前只在文档里，页面上完全看不到。**

用户带着「过滤」「多重鳞片」「毛皮大衣」时，详情页只说
「效果绝佳时伤害降低」，却看不出**只在效果绝佳时**才降 —— 而这是源码里 `if` 判定的。

### 18.8 又一个源码陷阱：`RESISTANCE(x)` 不等于 ×x

UI 走查时抓到一处矛盾：数据层写「极致蓬松：受到火属性招式伤害 **4 倍**」，
而表里算出来是 ×2.0。

回头查宏定义（`src/abilities.cc:133-138`）：

```c
#define MUL(val)        MUL_MODIFIER(modifier, val)
#define RESISTANCE(val) {                                  \
    MUL_MODIFIER(resistance, val);                         \
    MUL_MODIFIER(modifier,   val);                         \
}
```

`RESISTANCE(x)` 会**同时**往两个累乘器各乘一次 x —— 看着就是 ×x²。
如果真是这样，`RESISTANCE(2.0)` = 4 倍，数据层文案是对的，我的表错了。

顺着两个指针追下去（`src/battle_util.c:7041-7070`）：

```c
u16 CalculateAbilityMultipliers(..., u16* resistanceMultiplier) {
    u16 multiplier = UQ_4_12(1.0);
    ...
    ON_ABILITY(battlerDef, TRUE, gAbilities[ability].onDefensiveMultiplier,
        gAbilities[ability].onDefensiveMultiplier(battlerDef, ability, ..., resistanceMultiplier, &multiplier))
    return multiplier;          // ← 只返回 multiplier
}
```

再往上到唯一的调用方 `CalcFinalDmg`（`:7597-7612`）：

```c
u16 ignored;                    // :7602
...
MulModifier(&finalModifier, typeEffectivenessModifier);
MulModifier(&finalModifier,
    CalculateAbilityMultipliers(..., &ignored));   // :7612  ← 传的是 ignored
```

**`ignored` 声明后在全函数内再无任何读取。**`grep resistanceMultiplier -- 'src/'` 也只有这定义 + 3 处传递，没有真正的消费点。

**结论：`resistance` 分量在这版是死写，`RESISTANCE(x)` 的净效果 = ×x。**
所以数据层「4 倍」是**设计意图遗留**（旧版公式可能真把 resistance 表项算进去），
当前实现只有 ×2。表里写 ×2.0 是对的。

**核了另一分支**：`master` 的 `battle_util.c` 里**根本没有**
`onDefensiveMultiplier` / `CalculateAbilityMultipliers` —— 这套钩子是 upcoming 才有的。
而工具数据层 `ERDATA.abilities` 是 1034 条，正好对应 upcoming，
所以按 upcoming 判是对的。

**处理方式**：数值照源码（×2.0），另加一行浅色注解说明数据层文案与源码的差异。
注解不能走 `esc()` —— 见 18.9。

### 18.9 `esc()` 会剥掉带「源码」二字的句子

注解块一开始显示成一对方括号「［ ］」，内容是空的。
查 `esc`（`:1234`）：

```js
function esc(s){return scrubLeak(mdInline(String(s||'')))...}
```

`scrubLeak`（`:1216`）是「剥离内部实现痕迹」的过滤器，它的触发正则里**含 `源码`、
`口径`、`v\d.\d`、`[A-Z][A-Z0-9]*_[A-Z0-9_]+`、`L\d{2,5}` 等词**。
我的注解里有「源码是 RESISTANCE(2.0)」—— 两个触发词同时命中 ⇒ 整句被剥光 ⇒ 只剩方括号。

**这不是 bug，是刻意设计**（防止把实现细节漏给普通玩家）。
但它意味着：**凡是给玩家看的文案，都不能出现「源码」「口径」「A_B_C」这类词。**
注解这类纯手写常量不含用户输入，改为**不走 `esc`、直接字面拼接**即可。

### 18.11 减半特性没进全站：4 条漏网 + 倍率被写死成 0.5

`ABI_DMG_MOD` 表建好之后只在详情卡片里露脸。用户的原话是
「引水在属性克制那里倍率就变了……不止属性克制，工具其他地方也都要考虑」，
所以做了一次**全站对账**：把三张表的每个键喂给 `abiTagOf()`，看它能不能拿到标签。

```js
Object.keys(ABI_DMG_MOD).forEach(n => abiTagOf(n))
```

结果 A 表 15 条里有 **4 条返回 NULL**：

| 特性 | 源码倍率 | 数据层 |
|---|---|---|
| 厚脂 `THICK_BLUBBER` | 火/冰 ×0.25 | #889 ✓ 存在 |
| 熔岩铠甲 `MAGMA_ARMOR` | 水/冰 ×0.7 | 存在 |
| 遇水凝固 `WATER_COMPACTION` | 水 ×0.5 | 存在 |
| 黑暗亲和 `NOCTURNAL` | 恶/妖精 ×0.75 | 存在 |

也就是说：**玩家带着熔岩铠甲去查冰系弱点，表里仍然按原始相性算。**
这四条得补进 `ABI_TAG_PATCH`。

**但直接补会算错。**`defCellTrio` 里所有 hf 分支都写死 `*=0.5`：

```js
else if(ih.hf[at]==='天性')inn*=0.5;      // 硬编码
```

厚脂是 ×0.25、熔岩铠甲 ×0.7、黑暗亲和 ×0.75 —— 一律按 0.5 处理会失真。
所以给标签系统加一层 **`hfMul`（按属性给自定义倍率）**：

- `ABI_TAG_PATCH` 条目可写 `hfMul:{火:0.25,冰:0.25}`
- `abiTagOf` 合并 `hfMul` 进返回对象
- `abiImHf` 汇总各来源的 `hfMul`（取最严）
- `_hfMulOf(g,at)` 统一出口：**有自定义倍率用自定义，没有回退 0.5**

`defCellTrio` 里 5 处 `*0.5` 全部改走 `_hfMulOf`。
（默认仍 0.5，所以只有这 4 个特性受影响，其余全站行为不变。）

**实测确认接入生效：**

| 对象 | 属性 | 修前 opt | 修后 opt |
|---|---|---|---|
| 草苗龟（草系，带遇水凝固） | 水 | 0.5 | **0.25** = 0.5×0.5 |
| 幕下力士R（火系，带熔岩铠甲） | 冰 | 0.25 | **0.175** = 0.25×0.7 |

`opt` 是「勾选可选特性后的生效口径」，`defCellTrio` 的每一个消费点
（弱点表 / 六队共弱矩阵 / 联防配对 / 伤害判定 / 补联防推荐）都跟着变。
**这就是「工具各处都要体现」的落地方式：不新增展示，而是让已有的 40+ 处调用点拿到正确数值。**

### 18.12 两层机制的正确分工（避免把条件型硬塞进相性表）

这次对账也把边界定清楚了：

| 层 | 字段 | 是否进 `defCellTrio` | 原因 |
|---|---|---|---|
| 属性免疫 / 属性和减半 | `im` / `hf` / `hfMul` | **进** | 直接改写「某属性打它」的倍率 |
| 不分属性的减伤 | `def` / `phy` | **不进** | 与属性无关，改了会污染相性表 |
| 条件型减伤 | `cond` | **不进** | 依赖满血/天气/会心等战斗状态 |

B 表 11 条与 C 表 32 条之所以 `abiTagOf` 返回 NULL，**不是漏装，是本来就不该进**。
它们只在详情卡片展示。要做真正的数值链路（伤害计算器）才需要消费它们。

### 18.14 `mode:'floor'` 抬不动「无效」

接完 pick 之后实测「一般皮肤 + 小拉达 + 拍击打幽灵」，**结果仍是 0**。查规则：

```js
'一般皮肤':[{atk:['一般'],mul:1.0,mode:'floor'}]
// 实现：
else if(r.mode==='floor'){if(out>0&&out<r.mul)out=r.mul;}
```

`out>0` 这个前置条件把 0（无效）排除在外，于是**「把无效变成 1×」这件事永远做不到**。
而源码（`onTypeEffectiveness`）的写法是 `if (*mod < 1.0) *mod = 1.0` —— 0 也会被抬到 1.0。

去掉 `out>0` 即可。修后：拍击打幽灵 `0 → 1.0`；一般打钢 `0.5 → 1.0`（同源码口径）。

**这条正好是用户说的那句话的字面实现**：
「配招的时候就要考虑到自己特性可能会导致电反而克制地面系而不是免疫」。
「地面冲击」让电打地面从 0 变 0.5，靠的也是这条链路（`ABI_TE_CALC` + pick + floor）。

### 18.16 UI 可读性：字号偏小、主次不分（v4.208 / v4.209）

两个独立问题，分开处理。

**① 字号偏小（v4.208）**

全项目 421 处 `font-size` 全是硬编码 px（12 / 12.5 / 13.5 / 15 / 16.5 / 17.5 一档一档），
没有一个基准变量。逐条手改 421 处不现实，且历史上「顺序正则批量改字号」踩过连锁覆盖的坑。

做法：**一次 `re.sub` 回调**统一 ×1.08 并对齐到 0.5：

```python
pat = re.compile(r'font-size:\s*(\d+(?:\.\d+)?)px')
def cb(m):
    n = round(float(m.group(1)) * 1.08 * 2) / 2.0
    return 'font-size:%gpx' % n
s2 = pat.sub(cb, s)          # 单次 sub，回调里算，天然不连锁
```

关键在**用 `sub` 的回调而不是连续 `replace`**：`replace` 会把 `11px→12px` 之后的
`12px→13px` 再命中一次，字号一路飙；`sub` 一遍扫完，每个原文只处理一次。

实测 421 处全部命中，`node --check` 0 错、smoke 32/32；逐 tab 截图确认
（核心配队 / 招式反查 / 属性克制 / 速度线 / 队伍构建）无横向溢出、无卡片压扁。

**② 主次不分（v4.209）**

字号上来之后，卡片里「种族值 482」和标签「种族值」一样大，看不出哪个是核心信息。
而且**同一个信息在不同 tab 样式不一致**：队伍构建页早就写成
`种族值 <b style="font-size:17.5px">482</b>`，首页和宝可梦页却还是
`种族值（总值 482）` 一整句同字号。

统一为「标签 + 大号数字」：`种族值 <b style="font-size:19px">482</b>`，覆盖 2 处
（`renderSp` 的宝可梦页、`anp` 选择器），第 3 处队伍构建页本来就已经是强样式。

主 CTA「点击生成组队建议」原来是 `.mini` + `opacity:.75`，等于故意做淡；
改成 13.5px / 700 字重 / opacity 1，并加 `→`。

**层级结论**：中文名(19+) > 种族值数字(19, 主色) > CTA(13.5, 主色加粗) > 类型 chip > 英文名(11, 次要)。

**经验：同一个 UI 元素在多 tab 有多份渲染模板时，样式必须一起改**，
否则就是「一个页面看着挺好、换个页面又很弱」——本次「种族值」正是三份模板里改了两份。

### 18.17 伤害判定接入非属性减伤（v4.211 / v4.212 / v4.213）

#### 18.17.1 v4.211 是一次「先加后撤」——干燥皮肤火 ×1.25 不归 `ABI_TAG_PATCH` 管

`chk_dmgmod_all.py` 把 `ABI_DMG_MOD` 15 条全量喂 `abiTagOf` 后，`干燥皮肤`（#87，17 物种）显得「只登记了水免疫，火 ×1.25 丢了」。于是补了 `'干燥皮肤':{hf:['火'],hfMul:{火:1.25}}`。

**结果实测是错的**：蘑蘑菇 #285 火 `opt=3.125`，即 `2 × 1.25 × 1.25` —— 乘了两次。

根因在 `defCellTrio` L5118-5125 的 `mechRw` 机制层：

```js
if(mechRwOn()){
  var ma=mechDefAdjOf(s,at);
  if(ma.imm){if(inn>0)inn=0;if(opt>0)opt=0}
  else if(ma.hf){inn=inn*0.5;opt=opt*0.5}
  if(ma.down>1&&opt>0)opt=opt*ma.down;      // ← 干燥皮肤的火 ×1.25 在这里
}
```

`mechDefAdjOf`（L8875）读 `mechEvalOf(s,{})` 的 `defImm/defHf/defDown/defFlat`。干燥皮肤返回 `defImm=['水']` + `defDown=['火']`，**火 ×1.25 早就接好了**，它只写生效口径 `opt`（不动 `inn`），符合 L5116 注释「只正向调整」的纪律。

撤销后实测蘑蘑菇 #285：火 `base=2 inn=2 opt=2.5`（2×1.25）、水 `base=0.5 inn=0 opt=0`。已加注释留痕，防止以后有人再「补一次」。

**教训（写进台账）**：`mechRw` 机制层与 `ABI_TAG_PATCH` 是**并行两条路**，同一特性同一属性只能出现在一边。改 `ABI_TAG_PATCH` 前必须先跑 `mechEvalOf` 看 `defImm/defHf/defDown` 有没有它。

审计结果（`chk_mech.py`，8 条常见减半特性）：

| 特性 | `defImm` | `defHf` | `defDown` | 结论 |
|---|---|---|---|---|
| 厚脂肪 / 耐热 / 原木 / 免疫 / 深度冻结 / 重金属 / 坚实基础 | 空 | 空 | 空 | 归 `ABI_TAG_PATCH`，无重叠 |
| 超净 | `['水']` | 空 | 空 | **与 `ABI_DMG_MOD` 的「毒 ×0.5」矛盾，待核查** |
| 干燥皮肤 | `['水']` | 空 | `['火']` | 归 `mechRw`，**不要在 `ABI_TAG_PATCH` 登记** |

#### 18.17.2 v4.212：`dmgCalc` 从未算过非属性减伤

`dmgCalc`（L6541）此前只用 `eff=defCellTrio(sD,mType,null).opt` 拿属性相性，`ABI_DMG_ALL`（11 条不分属性）和 `ABI_DMG_COND`（32 条条件型）**只活在详情卡里，一点没进伤害**。而伤害判定 / OHKO 反解是工具里唯一真实消费伤害倍率的地方 —— 于是「多重鳞片满血 ×0.5」「毛皮大衣物理 ×0.5」这类减伤在 OHKO 判定里完全不存在，伤害偏高、结论偏乐观。

新增三个辅助函数（紧贴 `dmgCalc` 之前）：

- `dmgDefAbis(sD)` —— 防守方实际持有的特性名单：`inns` + `teamInfo[sD.id].pick` + 可选池 `abis`。**并入可选池是为了对齐 `defCellTrio` 的 `opt` 口径**（未勾选时按「池内最优」保守估算），与 L5099 的 `t.base.concat(t.inn).concat(t.ab)` 同构。
- `dmgCondHit(when,sD,sA,mType,isPhys,o,eff)` —— 只认静态可判定的条件：`物理招式`/`特殊招式` → `isPhys`；`满血时` → 恒真（保守按满血）；`效果绝佳` → `eff>=2`；`会心` → `o.crit`；`沙暴`/`冰雹|雪天` → `o.weather`；`攻方是X属性` → `sA.t1/t2`。**认不出的条件一律返回 false，宁可不计也不误乘**。
- `dmgDefAbiMul(sD,sA,mType,isPhys,o,eff)` —— 汇总倍率，返回 `{mul,hits}`，`hits` 记录命中明细（如 `多重鳞片×0.5(满血时)`）。

接入点固定在 `mod*=eff` 之后：

```js
var abiMul=1,abiHit=[];
try{var _dm=dmgDefAbiMul(sD,sA,mType,isPhys,o,eff);abiMul=_dm.mul;abiHit=_dm.hits;}catch(e){}
if(abiMul!==1)mod*=abiMul;
```

返回值加 `abiMul` / `abiHit`，原有字段一个没动（向后兼容）。

实测（`chk_dmgabi.py`，物攻 80+ 招打 100+ 攻端）：

| 防守方 | 特性 | `abiMul` | `abiHit` |
|---|---|---|---|
| 水跃鱼 | 多重鳞片 | 0.5 | `多重鳞片×0.5(满血时)` |
| 小海狮 | 毛皮大衣 | 0.5 | `毛皮大衣×0.5(物理招式)` |
| 超级布里卡隆 | 脑容量 | 0.5 | `脑容量×0.5(满血时)` |

`dmgRender` 的伤害行原来只有「克制 ×eff · 本系×1.5」。改为在末尾追加：

#### 18.19.4 踩坑：python 补丁里用 `rfind('return h}', start, end)` 永远找不到

#### 18.24.3 暗黑气场/妖精气场的关键细节：`APPLY_ON_ANY`

```cpp
constexpr Ability Impl<ABILITY_DARK_AURA> = {
    .onEntry = ...,
    .onOffensiveMultiplier = +[](ON_OFFENSIVE_MULTIPLIER) {
            if (moveType != TYPE_DARK) return;
            if (IsAbilityOnField(FALSE, [](AbilityEnum ability) -> int { return gAbilities[ability].auraBreak; }))
                MUL(.75);
            else
                MUL(1.33);
        },
    .onOffensiveMultiplierFor = APPLY_ON_ANY,
};
```

两个要点：
1. **倍率是 ×1.33 不是 ×1.5**（源码写死 `UQ_4_12` 前的浮点 `.75 / 1.33`）
2. **`APPLY_ON_ANY`** —— 场上**任何人**（包括对手）打出的恶招都吃这个加成，不是只给持有者
3. 若场上存在 `auraBreak`（气场破坏 `AURA_BREAK` #?）→ 翻转为 **×0.75**

工具里按「**持有者 = 我方出战术**」这一静态近似处理（只乘自己的招），详情卡注释已写明这条前提。
`妖精气场` 完全对称（`TYPE_FAIRY`）。

#### 18.24.4 深度冻结：两个方向各自成立

`深度冻结` #764（持有 6）在源码里有两条独立钩子：

- **进攻**：`.onOffensiveMultiplier` → `if (moveType == TYPE_ICE || moveType == TYPE_WATER) MUL(1.25)`
- **防守**：`.onDefensiveMultiplier` → 已在 `ABI_DMG_MOD` 里登记 `{t:[...],mul:0.5}`

以前只有防守侧接了，进攻侧漏掉。**同名特性在两条钩子上互相独立，不能因为「防守侧有」就认为「整个特性有了」。**

### 18.27 `.onModifyMoveFlags`：特性把招式「当成」某一类的三个例外（v4.234）

#### 18.27.1 `MoveFlag` 与 `FLAG_*` 是两层

`include/abilities.hh:125` 定义了 7 个抽象 `MoveFlag`：
```c
typedef enum {
    MOVE_FLAG_PUNCH = 1,
    MOVE_FLAG_KICK,
    MOVE_FLAG_SOUND,
    MOVE_FLAG_MEGA_LAUNCHER,
    MOVE_FLAG_DANCE,
    MOVE_FLAG_KEEN_EDGE,
    MOVE_FLAG_BONE,
} MoveFlag;
```

`DoesMoveMatchFlag`（`abilities.cc:331`）是两者之间的桥：
```c
int DoesMoveMatchFlag(ON_MODIFY_MOVE_FLAGS) {
    switch (flag) {
        case MOVE_FLAG_DANCE:         if (flags & FLAG_DANCE) return TRUE; break;
        case MOVE_FLAG_KICK:          if (flags & FLAG_STRIKER_BOOST) return TRUE; break;
        case MOVE_FLAG_MEGA_LAUNCHER: if (flags & FLAG_MEGA_LAUNCHER_BOOST) return TRUE; break;
        case MOVE_FLAG_PUNCH:         if (flags & FLAG_IRON_FIST_BOOST) return TRUE; break;
        case MOVE_FLAG_SOUND:         if (flags & FLAG_SOUND) return TRUE; break;
        case MOVE_FLAG_KEEN_EDGE:     if (flags & FLAG_KEEN_EDGE_BOOST) return TRUE; break;
        case MOVE_FLAG_BONE:          if (flags & FLAG_BONE_BASED) return TRUE; break;
        default: return FALSE;
    }
    /* 原始 flag 没命中 → 问每个特性自己的 onModifyMoveFlags 钩子 */
    return BattlerHasAbility(battler, FALSE, [&](int ability) -> int {
        CHECK(gAbilities[ability].onModifyMoveFlags)
        return gAbilities[ability].onModifyMoveFlags(battler, move, moveType, flag);
    });
}
```

**所以「原始 flag 命中」和「特性钩子命中」是 `或` 关系，不是叠加。**
这一点在实现时必须保证「同一 `mul` 只乘一次」，否则栗子斧吃「草属性 + 锐利」同一招会变成 ×1.69。

```js
var fs=ABI_FLAG_ATK[n];
```

### 18.28 速度修正型特性：一整列 `—` 的真相（v4.235）

#### 18.28.1 用户看到的现象

```js
var SPD_ABI=[
  {zh:'悠游自如',mul:1.5,cond:'rain',label:'雨天',src:'SWIFT_SWIM L868'},
  {zh:'叶绿素',mul:1.5,cond:'sun',label:'晴天',src:'CHLOROPHYLL L876'},
  {zh:'拨雪',mul:1.5,cond:'hail',label:'冰雹/雪天',src:'SLUSH_RUSH L2752'},
  ... /* 共 14 条，每条带源码行号 */
];
/* 返回 {zh,mul,label}；加速项优先（mul>1），全无加速才返回减速项。abis 与 inns 都要查。 */
function spdSpeedAbiOf(s){
  var pool=[].concat(s&&s.abis||[],s&&s.inns||[]);
  var up=null,dn=null;
  pool.forEach(function(a){
    SPD_ABI.forEach(function(r){ if(r.zh!==a)return;
      if(r.mul>1){ if(!up||r.mul>up.mul) up=r; } else { if(!dn||r.mul<dn.mul) dn=r; } });
  });
  return up||dn;
}
```

三条设计决策：
1. **加速项优先**——同时有轻装和慢启动时，显示玩家真正会用的那个。
2. **多加速取最高**——不做连乘（源码里多个 `.onStat` 是同一轮依次乘的，但同一只不可能同时满足雨天+晴天）。
3. **全无加速才显示减速项**——慢启动/铅质外壳是真实惩罚，玩家需要知道。

```js
function abiAtkKindOk(need,ctx,mvId){
  if(!need)return '无条件';
  if(!ctx)return null;
  if(need==='phys')return ctx.isPhys?'物理招':null;
  if(need==='spec')return ctx.spec?'特殊招':null;
```

### 18.30 状态型进攻增伤：毅力 / 决心 / 中毒激升（v4.237）

#### 18.30.1 源码里的「有状态」到底指什么

18.29 把这三条列为「静态算不了」，理由是「需自身异常状态，工具无此输入」。查源码后发现这个理由只对了一半 ——
条件确实需要状态，但函数名骗了人：

```cpp
// src/battle_util.c:9362
int HasAnyStatusOrAbility(int battler) {
    if (gBattleMons[battler].status1 && STATUS1_ANY) return TRUE;
    if (IsComatose(battler)) return TRUE;
    if (IsBloodStainAffected(battler)) return TRUE;
    return FALSE;
}
```

**名字叫 `HasAnyStatusOrAbility`，实际跟「特性」一点关系都没有**，三家是：任意异常状态、梦游（Comatose）、血染。

```cpp
// GUTS 毅力 abilities.cc:1263
if (HasAnyStatusOrAbility(battler) && IS_MOVE_PHYSICAL(move)) MUL(1.5);

// DETERMINATION 决心 abilities.cc:6565
if (HasAnyStatusOrAbility(battler) && IS_MOVE_SPECIAL(move)) MUL(1.5);

// TOXIC_BOOST 中毒激升
if (gBattleMons[battler].status1 & STATUS1_POISON_ANY && IS_MOVE_PHYSICAL(move)) MUL(1.5);
```

三者条件不同：毅力和决心是「任意异常」，中毒激升是「**只有**中毒/剧毒」，且都叠了物理/特殊的分流。

#### 18.30.2 输入面：攻方状态

`dmgCalc` 增加 `o.stA`，三档：

| 值 | 含义 |
|---|---|
| `''` | 无状态（默认） |
| `'any'` | 任意异常状态 → 满足 `HasAnyStatusOrAbility` 的第一条 |
| `'poison'` | 中毒或剧毒 → 同时满足 `hasAny` 与 `STATUS1_POISON_ANY` |

**`'poison'` 是 `'any'` 的子集**：毅力在中毒时也触发（`毅力[物理,中毒]=1.5` 已断言）。

UI 在伤害面板加一行 chip：`攻方状态：无 / 异常 / 中毒`，下方小字注明三条各自条件。
`dmgRender` 的 `o` 加 `stA:__spdSl.stA||''`，`dmgCalc` 透传进 `dmgAtkAbiMul` 的 `ctx`。

#### 18.30.3 新增 need 分支

```js
if(need==='stPhys') return (ctx&&ctx.stA&&ctx.isPhys)?…:null;
if(need==='stSpec') return (ctx&&ctx.stA&&ctx.spec)?…:null;
if(need==='poison') return (ctx&&ctx.stA==='poison'&&ctx.isPhys)?…:null;
```

**注意 `stPhys`/`stSpec` 只判 `ctx.stA` 非空**，不区分 `any`/`poison` —— 因为中毒本身也是异常。
`poison` 分支才做严格等值判断。

#### 18.30.4 实测

| 场景 | 结果 |
|---|---|
| 毅力 × 物理 × 无状态 | 1 |
| 毅力 × 物理 × 异常 | 1.5 |
| 毅力 × 物理 × 中毒 | 1.5 |
| 毅力 × 特殊 × 异常 | 1 |
| 决心 × 特殊 × 无状态 | 1 |
| 决心 × 特殊 × 异常 | 1.5 |
| 决心 × 物理 × 异常 | 1 |
| 中毒激升 × 物理 × 无状态 | 1 |
| 中毒激升 × 物理 × 异常 | **1**（关键：`any` 不等于中毒） |
| 中毒激升 × 物理 × 中毒 | 1.5 |
| 中毒激升 × 特殊 × 中毒 | 1 |

「中毒激升 × 物理 × 异常 = 1」是最容易写错的一格 —— 如果 `poison` 分支也写成「非空即触发」，
玩家选「异常」就会白拿 1.5，而那实际只是灼伤。

**覆盖**：毅力 38 只 + 决心 5 只 + 中毒激升 4 只 = 47 只。

### 18.31 顺带修掉一条断链：`surviveSolve` 从未定义，伤害面板一直是「渲染错误」（v4.237）

#### 18.31.1 现象

在 CDP 里直接调 `dmgRender('dmgOut2')` 看渲染结果，拿到的是：

```
渲染错误: surviveSolve is not defined
```

不是偶发 —— 每次渲染必现。

#### 18.31.2 定位

```bash
grep 'surviveSolve' index.html
```

只有 **2 处命中，全是调用点**：

```js
/* v4.95 A：防守向反推（同输入面，反向解「扛 N 下」） */
var sv1=surviveSolve(o,1),sv2=surviveSolve(o,2);
```

`function surviveSolve` / `surviveSolve=` 的搜索都是 0 命中。
`dmgRender` 整体包在 `try{…}catch(e){…}` 里，于是这个 `ReferenceError` 被兜成「渲染错误」，
**整个伤害判定面板（含 OHKO 判定、命中期望、16 段分布、耐久反推）全部不显示。**

这解释了为什么「🛡 耐久反推 · 扛 N 下」在用户视角里从来没出现过 —— 它不只是算得不对，是整块渲染挂在最后一步。

#### 18.31.3 重建

`ohkoSolveEv(o,hpD)` 是攻方向反解（扫 `evA` 直到 `r.lo>=hpD`）。守方向对称地扫 (HP EV, 防御 EV)：

```js
function surviveSolve(o,N){
  if(!o||!o.sD)return null;
  var isPhys=!!(mv&&mv[4]==='物理');
  for(var hpEv=0;hpEv<=252;hpEv+=4){
    var hp=dmgStatOf(bstI(o.sD,0),hpEv,31,0,'');
    for(var defEv=0;defEv<=252;defEv+=4){
      var r=dmgCalc({…,evD:defEv,…});
      if(r.hi*N<hp){ if(!best)best={hpEv,defEv,hp,dmgHi:r.hi}; break; }
    }
    if(best)break;
  }
  return best;
}
```

**两个必须注意的点：**

1. `dmgCalc` 的 `evD` 是**一个数字**，只作用于 `dIdx`（由 `isPhys` 决定是物防还是特防），
   **不影响 HP**。所以 HP 必须另外按 `dmgStatOf(bstI(sD,0), hpEv, 31, 0, '')` 算。
2. `hpEv` 外层递增 + 内层 `break` + 外层 `break`，保证拿到的是「第一个 HP 档里最小的防御投入」，
   而不是把所有解都收集再排序（那是 64×64 = 4096 次 `dmgCalc`，会卡）。

#### 18.31.4 复核

| 场景 | 基线伤害 / 对手 HP | 解 | 回代校验 |
|---|---|---|---|
| 波波拍击 → 小拉达，扛 1 下 | 58–68 / 96 | `hpEv 0 / defEv 0` | 68 < 96 ✓ |
| 同上，扛 2 下 | 同上 | `hpEv 0 / defEv 196`，max 降到 46 | 46×2=92 < 96 ✓ |

扛 1 下给 0/0 是**正确解**（68 < 96，本来就不用投 EV），不是没算 —— 这点在首轮用「拍击 → 耿鬼」测时
看起来像 bug（返回 `HP+0 / 物防+0`），实际是拍击对幽灵相性 ×0，伤害恒 0，当然一行 EV 都不用给。
**换成一一般系打普通系才看得出门槛。**
