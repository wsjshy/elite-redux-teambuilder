# ER 通用机制与招式/特性源码口径（2026-11-08）

> 本文回答一个问题：**玩家在 2.65 里实际感受到的规则，源码里到底是怎么写的**。
> 所有结论都标了源码位置，可以自己回查；查不到的就写「查不到」，不猜。

## 〇、先定口径：两个分支不是一回事

| 分支 | 最后提交 | 特性定义数 | 用途 |
|---|---|---|---|
| `master` | **2025-06-04** | **618 条**（`#define`，id 0–617） | **旧分支**，只能解释一年前那版 |
| `upcoming` | **2026-11-07** | **1073 个 `Impl<ABILITY_>` 名字** | **当前分支**，与游戏内 1034 个特性对得上 |

**这一节最初写反了，已更正。** 初稿把 `master` 当成「2.65 发行版对应代码」，
理由是它保留着 C 版 `battle_util.c`（694 KB）而 upcoming 只剩 441 KB。但真正的判据是**特性数量**：

- 游戏数据层 `ERDATA.abilities` 有 **1034 条**（id 0–1033，连续无缺口）；
- `master` 的 `include/constants/abilities.h` 只有 **618 条** `#define`，
  末条 `ABILITY_ROCKHARD_WILL 617`，`ABILITIES_COUNT_CUSTOM = ABILITY_ROCKHARD_WILL + 1` = **618**；
- `#733 拳舞`、`#788 冰川暴怒` 这类 id **在 master 里根本没有定义**（超出 617），
  只在 upcoming 的 `src/abilities.cc` 里存在。

**618 对 1034，缺 416 个特性 —— master 不可能是玩家在玩的这一版。**

### 0.1 那 416 个 id 怎么查

upcoming 把常量头文件改成了**生成式**（仓库里有 `.github/workflows/regenerate-ability-files.yml`），
`include/constants/abilities.h` 在 upcoming 的树里**整个文件不存在**，所以**没法按 id 查**。
替代路径是**按英文名对**：

| 项 | 数量 |
|---|---|
| 游戏特性总数 | 1034 |
| master 已定义（id 0–617） | 618 |
| 超出 master 的 | 416 |
| 其中能在 upcoming 按英文名匹配到 `Impl<ABILITY_>` | **397（95.4%）** |
| 两个分支都没有 | 19 |

那 19 条（如 `#628 Pretty Privilege`、`#629 Shallow Grave`、`#642 Jackhammer`）
在 master 和 upcoming 里都搜不到常量，属于**源码无法判定**，只能按数据层文案记录。

### 0.2 直接后果：163/164 的结论原来写错了

`ABILITY_TURBOBLAZE`（163 涡轮火焰）/ `ABILITY_TERAVOLT`（164 兆级电压）的「加属性」——
初版写「`AddBattlerType` 在 master 全仓 0 命中 → 2.65 里没有生效，是下一版预留」。
**这个推理把旧分支当成当前分支，结论是错的。**

upcoming 的 `src/abilities.cc:2256`：

```cpp
constexpr Ability Impl<ABILITY_TURBOBLAZE> = {
    .onEntry = +[](ON_ENTRY) -> int { return AddBattlerType(battler, TYPE_FIRE); },
    .onMoldBreaker = Impl<ABILITY_MOLD_BREAKER>.onMoldBreaker,
    .addsType = TYPE_FIRE,
};
```

`AddBattlerType`（`src/abilities.cc:227`）的实现是：

```cpp
static int AddBattlerType(u8 battler, Type type) {
    CHECK_NOT(IS_BATTLER_OF_TYPE(battler, type))   // 本来就是这个属性 → 不加
    gBattleMons[battler].type3 = type;             // 写进第三属性槽
    BattleScriptPushCursorAndCallback(BattleScript_BattlerAddedTheType);
    return TRUE;
}
```

**「加属性」= 写入 `type3`，是叠加出第三个属性，不是替换。** 并且本来就是该属性时不触发。

**方法论教训（已升级为红线）**：判断「源码里有没有」之前，先确认**这个分支对应哪个版本**。
用提交日期 + 数据层条目数两个独立指标交叉，比凭"哪个文件大"猜可靠得多。

## 一、伤害是怎么算出来的

源码：`src/battle_util.c:15056` `DoMoveDamageCalcInternal`

```
① 相性为 0 → 直接 return -1（打不动，连伤害数字都不算）
② power = CalcMoveBasePowerAfterModifiers(...)     ← 特性/道具/天气改威力都在这一步
③ dmg  = ((攻击方等级 * 2) / 5) + 2
④ dmg *= power
⑤ dmg *= CalcAttackStat(...)
⑥ dmg /= CalcDefenseStat(...)
⑦ dmg  = (dmg / 50) + 2
⑧ dmg  = CalcFinalDmg(...)                          ← 相性倍率、会心、随机数、道具、特性
⑨ Monotype Champ 修正（见第六节）
```

这是标准的 Gen3 公式骨架，②⑥⑤⑧ 是 ER 塞特性的地方。**排查「为什么这一下伤害不对」时，按 ①→⑨ 顺序找断点，比凭描述猜快得多。**

## 二、属性相性：ER 把它当「可改写量」

源码：`src/battle_util.c:15186` `MulByTypeEffectiveness`

正统作品里相性是死表。ER 把它做成**可被特性拦截并重写**的量，这就是为什么很多"本该免疫"的组合在 ER 里打得动。

### 2.1 特性改写（源码里逐个 `else if` 分支）

| 特性 | id | 触发条件（源码原文） | 相性被改成 |
|---|---|---|---|
| 一般皮肤 Normalize | 96 | 一般属性招式且原相性 ≠ 0 | **1.0**（无视抗性，见数据层"无视抗性"） |
| 胆量 Scrappy | 113 | 格斗/一般 → 幽灵 | 0 → **1.0** |
| 幻痛 Phantom Pain | 457 | 幽灵 → 一般 | 0 → **1.0** |
| 地面冲击 Ground Shock | 285 | 电 → 地面，且原相性为 0 | 0 → **0.5**（不是 1.0，是**抵抗**） |
| 电力过载 Overcharge | 349 | 电 → 电 | → **2.0**（效果绝佳） |
| 熔岩 Molten Down | 357 | 火 → 岩石 | → **2.0** |
| 岩浆吞噬者 Magma Eater | 467 | 火 → 岩石 | → **2.0** |
| 腐蚀 Corrosion | 212 | 毒 → 钢 | 0 → **2.0** |
| 压倒 Overwhelm | 328 | 龙 → 妖精 | 0 → **1.0** |
| 天使暴怒 Angel's Wrath | 439 | 毒针 → 钢 / 电网 → 地面 | → **2.0** |

**最容易算错的是「地面冲击」**：它写的是 `mod = 0.5`，也就是电属性招式打地面系**从免疫变成抵抗**，不是变成正常伤害。数据层写「改为抵抗」是对的，但玩家常按"能打"理解成 1 倍。

### 2.2 全局规则（不属于任何特性，人人都会遇到）

同一函数里，这几条**没有** `BATTLER_HAS_ABILITY` 前缀，属于通用修正：

| 条件 | 结果 | 源码 |
|---|---|---|
| `EFFECT_SLUDGE` 打水属性 | 2.0 | L15297 |
| `EFFECT_POISON_GAS` 打飞行属性 | 2.0 | L15299 |
| `MOVE_GIGATON_HAMMER` 打钢属性 | 2.0 | L15301 |
| 地面 → 飞行，**且目标已接地** | 0 → 1.0 | L15303 |
| 火 → 目标带 `tarShot` | 2.0 | L15305 |
| **强风天气（`WEATHER_STRONG_WINDS`）下，飞行系受到的 ≥2.0 相性** | **强制压回 1.0** | L15309-15313 |

最后一条最隐蔽：**强风一开，飞行系的弱点全部消失**。这是天气机制，不是特性，配招时不会有人提醒你。

## 三、能力等级倍率：标准 Gen3，没有魔改

源码：`src/pokemon.c:3545` `gStatStageRatios[MAX_STAT_STAGE + 1][2]`

```
-6: 10/40   -5: 10/35   -4: 10/30   -3: 10/25   -2: 10/20   -1: 10/15
 0: 10/10
+1: 15/10   +2: 20/10   +3: 25/10   +4: 30/10   +5: 35/10   +6: 40/10
```

即 ±1 为 1.5 倍 / 0.67 倍，±2 为 2 倍 / 0.5 倍，±6 为 4 倍 / 0.25 倍，**与官方一致**。
所以"能力等级被我算错了"这类问题，基本可以排除——除非涉及特性对**倍率本身**的改写（那是另一套逻辑，不在这个表里）。

## 四、招式效果：993 个 `EFFECT_`，不靠名字猜

- 招式数据：`src/data/battle_moves.h`（366,858 B，993 处 `EFFECT_` 引用）
- 效果实现：`src/battle_script_commands.c` 里 `case EFFECT_XXX:` 分支 + `data/battle_scripts_1.s` 汇编脚本

**结论：招式行为由 `EFFECT_` 分派，名字和描述只是标签。**
同一个 `EFFECT_` 可以挂很多招式（例如各种「附加异常状态」的招式共用一套代码，只有概率字段不同）。
因此**不要用招式名去推效果**，要查它挂的是哪个 `EFFECT_`，再去看那个 `EFFECT_` 的 case。

## 五、天气：ER 取消了传统的水/火属性天气加成

**这是最容易被正统作品经验误导的一条。**

正统 Gen3 及之后：晴天火系招式 ×1.5，雨天水系招式 ×1.5。**ER 里这两条都不存在。**

**证据**：在 `src/battle_util.c`（694,131 B 全文）、`src/battle_script_commands.c`、`src/battle_main.c`
里同时搜 `WEATHER_SUN_ANY` / `WEATHER_RAIN` 与 `UQ_4_12(1.5)` 或 `1.5`，
**命中数 0**。基础威力函数 `CalcMoveBasePowerAfterModifiers`（`src/battle_util.c:12838`）
从头到尾没有针对 `moveType` 的天气倍率分支。

**ER 里的天气只剩这些作用**：

| 类型 | 位置 | 实际作用 |
|---|---|---|
| 冰雹 `WEATHER_HAIL_ANY` | `battle_util.c:13983` | 特性 Whiteout 冰系招式 ×1.5（**靠特性，不是天气本身**） |
| 冰雹 | `battle_util.c:13317` | 特性 Christmas Spirit 使受到的伤害 ×0.5 |
| 沙暴 `WEATHER_SANDSTORM_ANY` | `battle_util.c:13324` | 特性 Dune Terror 使受到的伤害 ×0.65 |
| 强风 `WEATHER_STRONG_WINDS` | `battle_util.c:15309` | 飞行系受到的 ≥2.0 相性强制压回 1.0（**弱点全消失**） |
| 任意天气 | `battle_util.c:12638` | 气象球改属性与威力 |
| — | `battle_util.c:14730~14757` | `EFFECT_WEATHER_BOOST` 类招式按天气改威力 |

**配招含义**：不要为了"雨天水系加成"去堆水招，也不要指望晴天火系增伤。天气在 ER 里的价值集中在
① 场地/天气特效本身（如沙暴每回合削血）② 触发特定特性 ③ 让气象球/天气球系招式变强。

## 六、Monotype Champ：ER 自己加的一套修正

源码：`DoMoveDamageCalcInternal` 末尾 `switch (getMonotypeChampType())`

这是 ER 独有的，正统作品没有对应机制：

| Champ 类型 | 修正 |
|---|---|
| 草 / 超 / 电 / 毒 / 钢 | 对手不是玩家方 → 伤害 **减半** |
| 地面 / 格斗 | 对手不是玩家方，且相性 ≥ 2.0 → **减半** |
| 格斗 | 玩家防守、对方用格斗招式打过来 → **×2** |
| 冰 | 玩家防守、对方攻击 → **×2** |

换句话说，这四类 Champ 是**针对玩家方的难度调节**：前几类让对面打你更轻，格斗/冰反而让对面打你更重。

## 七、全量特性普查结论（游戏内 1034 条，旧分支仅覆盖 618）

方法：用 `include/constants/abilities.h` 的 `#define ABILITY_XXX <id>` 做 **id → 常量名**映射，再在 master 全仓 grep 每个常量。

> **为什么必须走 id**：数据层的英文名是压缩过的（`WandrngSprit`、`CuriusMedicn`、`Twist. Dimension`），由英文名推不出常量名。第一版按英文名推得 441 条「零命中」，全是假阴性。

### 6.1 覆盖率

| 项 | 数值 |
|---|---|
| 数据层特性条目（有 id） | 618 |
| 在源码中有引用 | **618 / 618** |
| 在「效果实现文件」中有引用 | **616** |
| 仅出现在 AI 判断 | **1**（#180 共生 Symbiosis） |
| 仅出现在声明与文本 | **1**（#600 龙族拳手 Brawling Wyvern） |

「效果实现文件」= `src/battle_util.c`、`src/battle_script_commands.c`、`data/battle_scripts_1.s`/`_2.s`、`src/battle_main.c`、`src/pokemon.c`。

### 6.2 复杂度分布

`src/battle_util.c` 内命中次数：min 0 / p25 1 / **p50 2** / p75 3 / max 17。

中位数只有 2，说明**绝大多数特性是「表驱动」或「单点判定」**，不是每条都有一段可叙述的复杂机制。
最多的几条：`#197 界限盾壳`、`#563 发号施令`（各 17），`#59 阴晴不定`（13），`#122 花之礼`（12），`#90 毒疗`（12）。

### 6.3 「读代码行自动生成效果摘要」这条路走不通

618 条里，只有 **34 条**的关键行带 `//` 注释（唯一可直接读出的语义来源），且集中在 `battle_ai_util.c`(273 行)、`battle_util.c`(203 行)。

反例：`#262 电晶体` 数据写「电属性招式威力提升至 1.5 倍」，但它在效果文件里只有 1 处引用、且那行不含任何数字——真正的倍率写在通用表里，单看常量的出现位置读不出效果。

**所以全量覆盖的正确形态是「覆盖率台账 + 少数高价值条目手工详解」，不是给 618 条各编一段散文。**

## 十、招式机制归类：950 招背后只有 402 个 `EFFECT_`

**招式行为不是由名字决定的，是由 `effect` 字段分派的。** 名字和描述只是标签。
所以判断一个新招"到底干什么"，第一步永远是看它的 `EFFECT_`。

- 950 个招式 → **402 个 distinct `EFFECT_`**
- 其中 **280 个 `EFFECT` 只挂 1 个招式**（专属实现，基本是作者为单个招写的脚本）
- 剩下 122 个 `EFFECT` 承担 670 个招式

**同一 `EFFECT_` 下的招式，附加机制完全一致，只是属性/威力/命中不同。** 这条对配招很有用：
想知道某招的附加效果，直接看它的同组兄弟就行。

### 7.3 一个必须知道的陷阱：`EFFECT_ARGUMENT_HIT`

有 13 个招式的 `EFFECT_` 是 `EFFECT_ARGUMENT_HIT`，这个名字本身说明不了任何事。
`data/battle_scripts_1.s:12061` 的脚本是：

```
BattleScript_EffectArgumentHit:
    argumenttomoveeffect
    goto BattleScript_EffectHit
```

而 `argumenttomoveeffect` 展开成 `various BS_ATTACKER, VARIOUS_ARGUMENT_TO_MOVE_EFFECT`，
对应 `src/battle_script_commands.c:10041`：

```c
case VARIOUS_ARGUMENT_TO_MOVE_EFFECT:
    gBattleScripting.moveEffect = gBattleMoves[gCurrentMove].argument;
```

**真实效果写在每个招式自己的 `.argument` 字段里**：

| 招式 | `.argument` | 实际效果 |
|---|---|---|
| Burning Jealousy 妒火 | `MOVE_EFFECT_BURN` | 100% 灼伤 |
| Alluring Voice 魅诱之声 | `MOVE_EFFECT_CONFUSION` | 100% 混乱 |
| Malignant Chain 邪毒锁链 | `MOVE_EFFECT_TOXIC` | 50% 剧毒 |

| Make It Rain 淘金潮 | `MOVE_EFFECT_SP_ATK_MINUS_1` | 自身特攻 −1 |

## 十一、`#513 小马之力`：描述写「锐利+神秘」，实际全招都吃 1.3 倍

`#513 ABILITY_PONY_POWER`，数据层描述只有四个字：**「锐利之刃+神秘之刃」**。
源码注释也写着 `// Combines Keen Edge & Mystic Blades.`。

按这个描述，玩家会以为它等价于「锐利之刃」或「神秘之刃」，即**只对锐利类招式加成**。实际不是。

`src/battle_util.c` 基础威力函数里的原文：

```c
// Mystic Blades
if(BATTLER_HAS_ABILITY(battlerAtk, ABILITY_PONY_POWER)){
    if (gBattleMoves[move].flags & FLAG_KEEN_EDGE_BOOST)
         MulModifier(&modifier, UQ_4_12(1.3));
         MulModifier(&modifier, UQ_4_12(1.3));   // ← 缩进在 if 内，语义在 if 外
}
```

**第二个 `MulModifier` 虽然缩进对齐到了 `if` 里面，但没有花括号，C 的语义是「`if` 只控制紧随的第一条语句」**，
所以第二行**无条件执行**。真实效果：

| 招式类型 | 实际倍率 |
|---|---|
| 锐利类（`FLAG_KEEN_EDGE_BOOST`） | 1.3 × 1.3 = **×1.69** |
| **其他所有招式** | 第二条单独生效 = **×1.3** |

**对照**：`ABILITY_KEEN_EDGE`（锐利之刃）和 `ABILITY_MYSTIC_BLADES`（神秘之刃）都只在锐利类招式上 ×1.3。
也就是说 **`#513` 比它号称「合并」的那两个特性强得多，因为它给全部招式都发了 1.3 倍**。

**判断口径**：这是一处漏花括号的代码瑕疵（大概率本想两条都在 `if` 内、做 1.69 的锐利加成，
结果第二条落到 `if` 外成了全招加成）。但**无论作者意图是什么，2.65 里的实际行为就是上表**。

**玩家含义**：看到「小马之力」不要按「锐利之刃」理解，它是一条**通用增伤 30%** 的特性，
配招时不需要专门堆锐利类招式去吃加成。

## 十二、破格穿透：白名单表已被废弃，改成特性自带 `breakable` 标志

**这是旧分支口径失效最彻底的一处。** 旧版（master, 2025-06）用一张中心表
`sAbilitiesAffectedByMoldBreaker`，108 条；当前分支（upcoming, 2026-11）**这张表整个不存在**
（全仓 0 命中），改成每个特性在自己的 `Impl<>` 里声明 `.breakable = TRUE`。

### 12.1 判定函数

`src/battle_util.c:9369`：

```c
int IsSuppressed(int battler, AbilityEnum ability, int checkMoldBreaker) {
    if ((checkMoldBreaker && battler != gBattlerAttacker && gHitMarker & HITMARKER_MOLD_BREAKER
         && gAbilities[ability].breakable) ||
        (((gFieldTimers.neutralizingGas && (B_NEUTRALIZING_GAS_WORKS_ON_INNATES || GetBattlerAbility(battler) == ability))
          || gStatuses3[battler] & STATUS3_GASTRO_ACID) && !IsUnsuppressableAbility(ability))) {
        return !DoesBattlerHaveAbilityShield(battler);
    }
    return FALSE;
}
```

**破格要穿透，四个条件缺一不可**：

1. `checkMoldBreaker` —— 调用方主动要求检查（不是所有判定都检查）；
2. `battler != gBattlerAttacker` —— **只有出招方穿透防守方**，反过来不行；
3. `gHitMarker & HITMARKER_MOLD_BREAKER` —— 本回合命中标记里带破格；
4. `gAbilities[ability].breakable` —— 目标那个特性**自己声明了可被破**。

### 12.2 规模：207，不是 108

统计 `src/abilities.cc` 里 1071 个 `Impl<>` 块：

| 项 | 数量 |
|---|---|
| `Impl<>` 块总数 | 1071 |
| 含 `.breakable` 声明 | **207**（全部为 `TRUE`，无一例 `FALSE`） |
| 旧分支白名单 | 108（已作废） |

**「破格只穿 1/6」这个说法在当前版本不成立** —— 207 / 1034 ≈ 20%，比旧版几乎翻倍。

### 12.3 一条对配招有用的边界：特性护盾能挡

`return !DoesBattlerHaveAbilityShield(battler);`
—— 目标持有道具 **Ability Shield（特性护盾）** 时，破格直接穿不进去。
这是打「破格队」时唯一一个不依赖特性、纯靠道具的反制手段。

### 12.4 不可被破的

破格三兄弟自己（`MOLD_BREAKER` / `TURBOBLAZE` / `TERAVOLT`）在 `abilities.cc` 里用的是
`.onMoldBreaker`（声明「我是破格系」），**不是** `.breakable`（声明「我可被破」），
所以它们本身穿不进彼此。同类的还有 `BLIND_RAGE`、`OVERRULE`。

### 12.5 落页面

`index.html` 的 `ABI_DETAIL['104']`（破格）已整块重写为 6 行：
判定条件 / 穿透得到 / 穿透不到 / 会被挡下 / 会失效 / 先天槽同样穿透。
163、164 的「穿透范围」行同步改成「207 个 breakable」，探针 D3/D4 断言一并改为 `breakable` + `207`。
