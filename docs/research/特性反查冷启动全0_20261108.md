## 三、因果链（行号与代码原文，均指 `c87828c`）

1. **解析到此处就无条件渲染**，没有任何就绪判据。L5316-5319：

```js
(function(){
  $('abiSearch').oninput=function(){renderAbi()};
  renderAbi();
})();
```

2. **数据到达时机**：能力表（abilities 等主数据）在同步的 `data_lite_v498.js` 里，所以首次
   渲染时「能力」已经在；但物种分片 `data_species_v498.js`（1,362,446 B）是在
   `window load + 800ms` 才异步加载的（L1072：`__loadShard('species',...)` /
   `__loadShard('adv',...)`）。**能力表已到、物种表没到**——这两件事同时成立正是该 bug 的指纹。

3. **空返回不写缓存**：`abiOwners()`（L5564-5577）开头有

```js
if(!ERDATA.species||!ERDATA.species.length)return {};
```

   物种为空时直接返回 `{}`，且**不写缓存**。所以首次渲染拿到 `own={}`。

4. **全 0 产出**：`renderAbi()` 的 L5664-5666 拿到 `{ab:[],inn:[]}`，每张卡「天性 0 /
   可选 0」，`_hidN` 累加为 0；L5712 写出「匹配 60 个特性 · 开关隐藏 0 个持有者条目」。

5. **数据到了也不补渲**：`er-ready` 事件在该版本没有任何特性反查的监听者 ⇒ 800ms 后
   物种数据到达也不会重渲，页面停在全 0，直到用户手动 toggle 走 `abiFilterToggle()`
   （L5639-5644）重渲——这正是用户「关掉再打开就正常」的来源。

一句话定性：**不是「永不渲染」，而是「在不该渲染的时机渲染了」**——渲染确实发生过
（状态条文案就是证据），只是发生在物种分片到达之前。

## 六、残留风险与加固理由

`er-ready` 由 `__erPending` 脚本计数归零派发（L1070-1071），而分片 `onerror` 路径
（L1067 尾部）**同样会递减计数**并置 `window.__ER_PARTIAL=true`。也就是说：当 species
分片加载失败时，`er-ready` 会在 **species 缺失**的情况下照常派发——`bb315b9` 的旧逻辑
此刻仍会画出 60 张「0/0」的误导卡。

`c21e9f7` 改以 `ERDATA.species.length` 为就绪判据：事件到了但物种数据没到（含 onerror
兜底场景），就不渲染误导卡，等 `er-shard-species` 真正带数据来再补渲。这是本次加固相对
`bb315b9` 的净增价值。

## 七、与既有文档的差异

`docs/research/技术债定级_20261108.md` L66-71 把「特性反查门控用一次性事件、事件错过就
永不渲染」列为「全 0 现场最可能的来源」（原文：「若事件在 Tab 打开之前就发完了，这个
addEventListener 挂在上面永远等不到第二次 → 该 Tab 不渲染」）。

**该结论已被实测推翻**，推翻证据有三：

1. 状态条文案「匹配 60 个特性 · 开关隐藏 N 个持有者条目」只可能由 `renderAbi()` 内
   L5712 写入——静态 HTML 中 `#abiFiltStat`（L986）是空的。用户截图里这条文案存在
   ⇒ 渲染确实发生过，不是「永不渲染」。
2. `c87828c` 的 IIFE（L5316-5319）在解析时就无条件调了 `renderAbi()`，发生在物种分片
   load+800ms 到达之前。
3. 历史快照探针实测：冷启动就有 15 张全 0 的卡 + 状态条「隐藏 0」，toggle 后变正常——
   渲染过了，只是时机错。

正确定性是「**在不该渲染的时机渲染了 + 数据到达后无补渲入口**」，而不是「事件错过导致
永不渲染」。该既有文档原文未动（规程：新增 md，不改既有文档）。
