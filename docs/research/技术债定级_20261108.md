> **口径澄清（收尾时补）**：这里的"P0 = 0"指**静态审计**（扫代码模式）没能在这些长期被记作"技术债"的项里找出用户可感知的缺陷。
> 而用户实际遭遇的那个 bug（特性反查冷启动全 0）**本来就不在静态审计的视野里**——它是运行时竞态，同一份代码在 headless 快照上可以完全复现、也可以完全不复现。
> 它最终靠**历史快照实跑**才定性并修掉（详见 `特性反查冷启动全0_20261108.md`）。这两件事不矛盾：**能静态判死的债确实为 0，但"静态扫不出来"不等于"没有 bug"**。

## 二、inline onclick：虚惊一场

| 指标 | 数值 |
|---|---|
| `onclick="..."` 属性数 | **199** |
| 去重后被调用函数数 | **126** |
| 其中在文件里找不到定义的 | **13** |
| 那 13 个的真身 | 全部是**对象方法调用**：`stopPropagation`(27)、`getElementById`(6)、`filter`(4)、`reload`(2)、`click`、`scrollIntoView`、`slice`、`join`、`find`、`remove`、`Error`、`map`、`forEach` |

也就是说：**真正断链的全局函数 = 0**。之前把「193 处 inline onclick」记成技术债，实际风险为零——它只是写法老派，不是坑。

**不建议改的理由**：把这 199 处改成事件委托，要动到渲染函数里的模板字符串，而这个项目已经踩过「模板字符串里 inline onclick 引用渲染函数局部对象，异步触发时作用域失效」的坑（解法是渲染时预绑定到 window）。改一遍的收益是"代码好看"，代价是重新引入一类已修过的 bug。**不改。**

`catch` 总数 **585**（注意：AGENTS 里原来记的「369 处静默 catch」不准确，实测**完全静默的是 368 条**，占 62.9%）。

按"被包住的是什么"分类：

| 类别 | 条数 | 性质 |
|---|---|---|
| **C. 渲染函数被静默吞** | **41** | **P1 —— 见下** |
| A. DOM 存在性检查 | 19 | 合理（`if(el) el.classList.remove('open')`，元素不存在就跳过） |

### P1 的具体机制（为什么它会让用户以为"功能坏了"）

失败的形态不是报错，而是**静默的"什么都没发生"**：

1. **队伍变更后三个渲染各自失联**（约 L3185–L3188，搜 `closeAnPicker()` 定位）
```js
closeAnPicker();
try{renderTm(true)}catch(e1){}      // 队伍网格
try{renderSlots()}catch(e2){}        // 槽位
try{renderAnalyze()}catch(e3){}      // 分析
try{saveTeam()}                      // ← 数据照常落盘
```
任一渲染抛错 → **界面停在旧状态，但底层 `team` 已经改了并已保存**。用户看到的就是"点了没反应"或"显示和实际不一致"；再点一次触发别的路径重渲，就"突然对了"。这与用户报的「关闭再打开就正常了」是同一类症状模式。

2. **速度线与核心列表被空 catch 包住**（约 L2234）
```js
setTimeout(function(){try{speedRender(true)}catch(e){};
  try{if(window._initCoreList)window._initCoreList()}catch(e){};
  try{if(typeof renderRecentChips==='function')renderRecentChips()}catch(e){}...})
```
`speedRender` 一旦抛错，速度线页就是空白，且没有任何痕迹。

3. **特性反查的渲染门控「就绪判据不校验数据」**（约 L5548，搜 `__erReady` 定位）

> **2026-11-08 已实测复现、修复并上线（v4.185，详见 `特性反查冷启动全0_20261108.md`）。下面这段初始推断只对了一半，原文保留以记录裁决轨迹。**

```js
if(window.__erReady){renderAbi();}
else{document.addEventListener('er-ready',function(){try{renderAbi()}catch(e){}});}
```

当时推断「`er-ready` 只派发一次，事件错过就永不渲染」。**实测推翻了这个机制**：在历史快照 `c87828c`（`bb315b9^`）上冷启动真复现了 15 张卡全 0/0、toggle 后恢复，但真因不是"事件错过"，而是三件事叠加：

1. `er-ready` 的判据是 `__erPending` 脚本计数归零（onload/onerror 都算），**不校验 `ERDATA.species` 是否真的写入**
2. `species` 分片的 `onload` 先于数据就位触发（网络竞态）时，`renderAbi` 用空 species 渲染，`abiOwners()` 返回 `{}`（空返回不写缓存）
3. 关键：`er-shard-species` **当时没有任何补渲监听** → 数据到了也不刷新，界面停在 60 张「天性 0 / 可选 0」的卡壳上，直到用户手动 toggle 触发重渲（这就是用户说的"关闭再打开就正常了"）

修法：以 `ERDATA.species.length` 为真实就绪判据，同时监听 `er-shard-species` 与 `er-ready` 补渲，并失效 `_abiOwners` 缓存。**未改开关默认值**（符合用户约束）。

4. **注释自承的初始化顺序债**（约 L4072–L4073）
```js
/* ...顶层立即调用会在 NM2ID 初始化前抛错并中断整块执行 → 延迟到本脚本块结束后执行 */
setTimeout(function(){try{renderAnalyze()}catch(e){}},0);
```
用 `setTimeout` 绕过初始化顺序，本身没崩，但它把"顺序依赖"藏进了时序里——以后谁调整脚本块顺序，这类静默吞就会变成真 bug。

### 为什么 P1 但不建议立刻大改

41 处里绝大部分是「用 try 包一层防崩」的善意写法，直接把空 catch 补成 `console.warn` **不解决任何问题**（用户看不到 console）。真正的修法只有两类：
- **把「失败静默」改成「失败可见且可恢复」**：渲染失败时至少留下可检测状态（如置一个 `__renderFail` 标志、或走兜底渲染），而不是让界面停在旧内容
- **把「一次性事件门控」改成「条件式门控」**：每次进入都检查数据是否就绪，就绪就渲染、未就绪则既监听事件也主动补一次

这两类都属于结构性改动，应当**与具体 bug 绑定着改**（有现场、能验证），而不是为了"清理技术债"批量改。

## 五、关于「242 个顶层 var」

本次没有把它列成独立风险项，原因是：**顶层 `var` 的风险只有一个——与函数名或后来引入的库撞名**。而 §二 已经证明 199 处 inline onclick 的 126 个被调函数全部有定义，`window.` 前缀定义的函数也都在集合里，说明当前没有发生撞名失效。真要防，靠一次性改名是防不住的（改名会连带改所有引用点）；更划算的做法是**在 smoke 里加一条"window 上的全局函数名去重"断言**，每次构建自动检查。这条建议留给后续，本次不实施。

### 这条负结论值钱在哪

它说明：**静态审计只能"提出嫌疑"，不能"定级"。** 三条嫌疑里，两条源于我读代码不完整（`onerror` 那行有 503 个字符，只看了前 390 个），一条是把防御性代码当成了缺陷。若按嫌疑直接改，就是往一条健康的异常路径里塞 16 行"修不存在的 bug"的代码 —— 这正是本项目反复踩过的坑。

**方法论沉淀：任何"异常路径缺陷"在定级前，必须构造出它真正触发的运行时场景、跑改前/改后对照；跑不出差异的，一律不算缺陷。**

## 七、建议的执行顺序

1. **先修那个已被用户实际遇到的 bug**（特性反查全 0）——有现场、能验证、用户能感知（另一执行方正在做）
2. 若上述修复需要动到渲染门控，**顺手把同类的一次性事件门控一并排查**（全文件搜 `addEventListener` + `er-ready`），但只改"有同类失效路径"的，不批量
3. 渲染静默吞（41 处）**不单独发起清理**，只在每次真修某个 bug 时，把该 bug 附近的那一处改成"失败可见"
4. inline onclick、顶层 var：**不动**
