# v4.400 机制前缀「强化」「接棒」名实校验

> 版本 v4.400 ｜ 日期 2026-11-17 ｜ 基线 v4.399（gh-pages `5b253bb`）

## 一、问题从哪来

用户诉求是「让工具更好用、推荐更精准」。上一版 v4.399 修掉的是**跨卡重复**（同一物种两张卡配置逐字节相同），这一版转向**卡内名实**——卡片名字承诺的东西，四招里到底有没有。

量化探针（全库 1906 物种 × 六人队/空队）：

| 前缀 | 名含（六/空） | 四招无对应机制 | 说明 |
|---|---|---|---|
| 强化 | 1571 / 1414 | **70 / 51** | 真缺陷 |
| 场地 | 124 / 116 | 124 / 116 | **假阳性**（见第四节） |
| 接棒 | 5 / 8 | **4 / 7** | 真缺陷（需按换人招重判） |
| 空间 | 69 / 95 | 0 / 0 | 正常 |
| 顺风 | 195 / 210 | 0 / 0 | 正常 |
| 钉子 | 276 / 367 | 0 / 0 | 正常 |

「强化」70 张去掉前缀后的落词分布：

```
轮转补盲 43   受队消耗 20   输出压制 3   主力输出压制 2
替身流 1      慢速重炮 1
```

## 二、根因：两层错位

### 第一层：前缀按「物种能学」判，却贴在「流派卡」上

```js
function mechPrefix(p){            // p 是 profile（物种级）
  ...
  if(p.hasBoost)return '强化';     // hasBoost = fn.boost = 该物种「能学」强化招
  if(p.hasPass)return '接棒';      // hasPass  = 该物种「能学」接棒
  ...
}
```

调用点 `pref=mechPrefix(p)` 在 `_deriveBuildsCore` 里**按物种算一次**，然后：

```js
var nm=(pref&&c.base.indexOf(pref)<0?pref:'')+c.base;   // 前缀加到**所有**候选 base 上
```

所以：**一个物种能学剑舞 → 它名下全部流派都冠「强化」**，包括本来就不带强化招的「轮转补盲」「受队消耗」。

这与项目铁律「能学≠会带」直接冲突。

实例（六人队）：

| 卡 | 名 | 四招 |
|---|---|---|
| #56 猴怪[?] | 强化轮转补盲 | 真气拳 / 泄愤 / 岩石封锁 / 急速折返 |
| #36 皮可西[3] | 强化受队消耗 | 月光 / 电磁波 / 光墙 / 守住 |
| #262 某物种 | 强化输出压制 | 欺诈 / 突袭 / 替身 / 嬉闹 |

三条全无强化招，但名字都说「强化」。

### 第二层：原有校验只覆盖 roleTag==='强化'

引擎本来就有校验（v45-2）：

```js
if(roleTag==='强化'){                          // ← 只对 roleTag 恰好是「强化」的卡生效
  var _hasB=(b.mv.main||[]).some(sl => (sl.kind||mvKindOf(sl.id))==='boost');
  if(!_hasB){ /* 有可学强化招则补入；无则改名 */ }
}
```

上面 70 张的 `roleTag` 是「轮转」「受队」，**完全绕过校验**。

更隐蔽的一处：`roleTag` 按 `c.tag`（候选生成期）赋值，而 v4.393 的 roleTag 重算块排在 v45-2 **之后**。于是出现「校验时不是强化、重算后变成强化」的卡——

**#1788「替身强化流」**：`roleTag='强化'`，四招 `替身 / 守住 / 电磁波 / 蹭蹭脸颊`，没有一条强化招。它正好落在两层错位的夹缝里。

## 三、修法：去前缀，不补招

### 为什么不去补招

v45-2 的「有可学强化招就补入」看起来能让名字兑现，但那是把「能学」变成「硬带」——正是 v4.371 用户拍板否决的「平铺近同流派」。这 43 张「强化轮转补盲」的物种全都「能学」剑舞，若补进去，轮转卡就变成「轮转 + 强化」双轴，挤掉一个攻击位，打法被硬改。

**采用与 v4.394「强化清场」完全一致的口径**：名字承诺的机制必须在四招里兑现，否则改名，不动招。

### 判据

| 项 | 取值 | 理由 |
|---|---|---|
| 强化招 | 16 词名正则 `/剑舞\|龙之舞\|蝶舞\|冥想\|诡计\|诅咒\|健美\|巨大化\|破壳\|腹鼓\|磨爪\|铁壁\|集气\|自我激励\|生长\|宇宙力量/` | 与 v4.391 `_v391bst` / v4.392 `_v392BST` / v4.394 `_v394BST` **同字面** |
| 不用 `FUNC_MV.boost` | 该表 11 项 | 它是**选招权重**口径，缺 生长74 / 瑜伽96 / 诅咒174 / 宇宙力量322，与「名字是否兑现」不是同一个用途 |
| 接棒 | 接棒 226 **或** `FUNC_MV.pivot`（369 急速折返 / 521 伏特替换） | 引用真源，不手抄；接棒语义可由换人招承担 |
| 去前缀后落「主力输出压制」 | 复用 v4.391 两道门：`max(攻,特攻) ≥ POWER_OK(95)` 且实配伤害招 ≥2 | 避免「同一指标两处矛盾」（v4.391 踩过的坑） |

只改 `name`，`side` / `roleTag` / 招组 / EV / 道具 / 特性 / 排序 一律不动。

### 插入位置

在 `}catch(eV4396){eV4396.name}` 之后、v4.399 块之前 —— **必须排在 v4.399 的重复复查之前**，因为改名可能让两张卡变成同名同配置，要留给 v4.399 去合并。

## 四、「场地」124 张为什么判为假阳性

探针报「名含场地 124 / 四招无场地招 124」，100% 不符。但这不是缺陷：

```js
if(f.length)return '场地';   // f = p.field = profile.field = ab.sys
```

`p.field` 是**该物种能开的体系**（走特性口径，如「电气制造者」），不是「自带场地招」。`basis` 里也明确写着：

```
体系 电场（自我设置）
```

即「场地」前缀表示「这张卡依赖场地增伤」，皮卡丘带伏特攻击时电场增伤 30%，语义准确。**探针把「场地」错解成「自带场地招」才报 124/124**，这是探针缺陷而非引擎缺陷。

## 六、新增常驻断言

在 `tools/headless/verify_invariants.js` 加两条（按「名实断言统一走 verify_invariants，加规则只加一条 INV」纪律）：

- **INV14**：名含「强化」→ 必带强化招（覆盖非「强化清场」形态）。口径与 INV01 完全一致（`FUNC_MV.boost ∪ BSTR 名字`）。适用 **2864** 张，违规 0。
- **INV15**：名含「接棒」→ 必须带接棒 226 或换人招（`FUNC_MV.pivot`）。适用 **2** 张，违规 0。

同时在 `tools/smoke.js` 加一条**结构断言**：四处强化招正则副本（`_v391bst` / `_v392BST` / `_v394BST` / `_v400BST`）必须同字面、恰好 4 处。因为它们都是块内局部变量、作用域互不可见，无法直接引用同一常量，只能靠断言锁死字面，防止某处单独漂移重演「同一指标两处矛盾」。

> 注：引擎里另有多套不同字面的强化词表（如 `/剑舞|腹鼓|健美|龙舞|.../` 17 项旧表），用途不同，不纳入本检查。检查只锁以「剑舞|龙之舞|蝶舞|冥想|诡计|诅咒」开头的那一种。

## 八、工程踩坑（长期记）

1. **`io.open(p, encoding='utf-8').read()` 会把 CRLF 归一成 LF**。universal newlines 默认开启，读进来的字符串已无 `\r`，写回就是纯 LF——本次一度把 CRLF 24,018 写成 0、bare LF 涨到 24,130。**读写 index.html 必须 `newline=''`**，或走 `rb` 字节路径。
2. **PowerShell 里反引号是转义符**，`python -c` 内联脚本里拼含反引号的字符串（Markdown 代码标记）会被吃掉，导致 `assert count==1` 失败。此类替换一律写成 `.py` 文件，用 `chr(96)` 或三引号规避。
3. **改名块必须排在重复复查块之前**。v4.399 的重复复查在链尾，v4.400 的改名块插在它前面，改名产生的新重复才能被同一次运行清掉。
4. **门禁的 `total` 与 `offHist` 都是空队口径**，六人队 74 张改名在 gate 里看不出来，必须配快照 diff 才能证明。
