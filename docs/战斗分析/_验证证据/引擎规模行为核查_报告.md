### 2.3 规模公式（机制解释）

18 核心汇总：**每位队友闭合 2.2–3.0 条需求** = 自身 1 条 + 多功能（`MULTI_MAX=2` 上限 2 条）

```
输出人数 ≈ 1 + (需求条数 − 核心自满足) / (1 + 多功能闭合数)    ，上限 MAX_TEAM = 6
```

实测吻合：坚果哑铃 (9−1)/2.67=3 → 4 人；土王 (10−1)/3=3 → 4 人；大比鸟 (10−0)/2.7≈3.7 → 5 人；妙蛙花 (15−2)/2.6=5 → 触顶 6 人。

**所以规模小的情形发生在「需求条数少」（受队/单侧核心 9–11 条）而非「候选被砍」。**

### 2.4 反事实归因（**仅内存改常量，不改文件**）

| 反事实（内存） | 均值人数 | 分布 | 停止原因 | 读法 |
|---|---|---|---|---|
| 基线（`STOP_PRIORITY=1, MULTI_MAX=2`） | **5.333** | 4:2 / 5:8 / 6:8 | 满员 8 / 清零 10 / 低优先 0 | 现状 |
| `STOP_PRIORITY=2` | 5.000 | 4:5 / 5:8 / 6:5 | 低优先 6 / 满员 5 / 清零 7 | 阈值**上调反而更小**（放弃低优先需求） |
| `STOP_PRIORITY=3` | 4.500 | 3:1 / 4:9 / 5:6 / 6:2 | 低优先 12 | 同上，压缩更明显 |
| **`MULTI_MAX=0`**（关闭多功能合并） | **6.000** | **6:18** | 满员 18 | **多功能合并是规模收缩的唯一主因** |
| `MULTI_MAX=4` | 3.833 | 3:5 / 4:11 / 5:2 | 清零 18 | 合并越强 → 队伍越短 |

**两个可直接引用的结论**
1. `STOP_PRIORITY=1` 是**死代码**：18 核心命中 0 次；需求最小优先级恒为 1，`priority < 1` 永不成立。L5165 分支与 UI 文案「剩余最高优先级 < 1 → 立即停手」在当前常量下**不可能触发**（若未来要做「按优先级截断」，需改为 `<= STOP_PRIORITY`）。
2. 规模的一阶杠杆是 **`MULTI_MAX`（多功能合并上限）**，且方向是「合并越强、队伍越短」；`MAX_TEAM=6` 才是上限硬约束（8/18 触顶）。

## 3. 「平均 3.60 人」的来历（评测口径分解）

### 3.1 `3.60` 的确切出处

`nn_data\g4_spotcheck.json`：

```
scorers.engine_E.topk_mean_size = 3.6        topk_size_hist = {3:5, 4:4, 5:1}
scorers.engine_E.rho_vs_size    = -0.2714 (p=6.87e-29)     ← 引擎指标与规模负相关
rho_win_vs_size                 =  0.7232 (p≈0)            ← 真值胜率与规模强正相关
n_test = 1628    size_counts_test = {3:588, 4:431, 5:383, 6:226}
```

即：`3.60` = **在该评测池内、按引擎自身分（`engine_meanMemberScore` = 成员均值）取 top-10 的团队规模均值**。它不是「引擎推荐的平均规模」。

### 3.2 池是怎么造出来的（`nn_data\gen_engine_samples.py` L172-199 + `g4_pool_build.py`）

| 构造模式 | 定义（源码） | 行数 | 规模均值 | 规模分布 | 真值胜率均值 |
|---|---|---|---|---|---|
| **A** | `ids = base_ids`（**引擎原方案，未改动**） | **175** | **5.72** | 4:1 / 5:47 / **6:127（72.6%）** | **0.7907** |
| **B** | 引擎方案**删 1–2 人**（`rng.sample` drop） | 1556 | 4.153 | 3:294 / 4:730 / 5:532 | 0.5288 |
| **C** | 引擎方案**换 1–2 人**为随机池内成员 | 1109 | 5.5518 | 4:37 / 5:423 / 6:649 | 0.6527 |
| **D** | **随机组队**（`k=rng.randint(2,5)`，与引擎逻辑无关） | 1122 | 3.8717 | **3:528（47.1%）** / 4:318 / 5:168 / 6:108 | 0.2367 |
| 合计 | 过滤 `size>=3` + 按 team_ids 去重 | 3962 | 4.5341 | 3:822 / 4:1086 / 5:1170 / 6:884 | 0.4923 |

**三重口径效应**
1. **构造混入**：真正代表引擎行为的只有 **mode A（4.4%）**，其规模均值 **5.72、最小 5、72.6% 恰好满 6**；而占 **67.6%** 的 mode B（删人）+ mode D（随机）把池均值压到 4.53。
2. **过滤截断**：`g4_pool_build.py --min-size 3` 把 size<3 的样本整批剔除（mode D 存在 1–2 人的可能），池的规模分布被裁剪成 3–6。
3. **指标规模偏置**：`meanMemberScore` 是**成员分均值**，队伍越短越少「拖均值」的槽位 → 与规模负相关（**−0.2714**）→ 池内 top-10 被短队（B/D 造的 3–4 人）占据（hist `{3:5, 4:4, 5:1}`）→ **3.60**。

### 3.3 规模混淆的另一半

`winrate_by_size`（本池 3962 行）：3 人 **0.1696** / 4 人 **0.4169** / 5 人 **0.5895** / 6 人 **0.7562**（rho_win_vs_size **0.7232**）。

→ 在「把所有模式混在一起」的池里，规模几乎就是标签本身；这也正是 G4 线「规模受控后引擎 size-6 层反优于 NN」的由来。**用混合池 + 均值型指标得出的「引擎推荐平均 3.60 人」不能作为引擎行为的证据。**

## 5. 规模推荐行为改进建议（**交用户产品拍板，本次未实施**）

**G1（评估侧，建议优先）**——修正「引擎推荐规模」的测法与结论表述
1. 规模统计**只用 mode A**（或按 mode 分层报告），避免把 mode B/D 的构造规模记到引擎头上；全池口径必须标注「含删人/换人/随机构造」。
2. 规模相关指标改用**规模中性**版本：如 `assignedSum`（和）或对 size 做回归剔除后的残差；若坚持用 `meanMemberScore`，须显式声明其与 size 负相关（rho −0.2714），top-K 统计**必须分规模分层**（同 size 内比 top-K）。
3. 「引擎 top-K 平均规模」这一指标本身应**废止**或改名为「池内 top-K 样本的规模构成」——它度量的是池，不是引擎。

**G2（产品侧，可选，不改变现状的默认行为）**——若希望玩家更常看到满 6 编队
- 提供**目标队伍规模**参数（默认「需求驱动（4–6）」/ 可选「满编 6」）与方案卡上的「继续补位」按钮：把剩余 `open` 需求与「低优先但正向」的候选依次补到 6，并在每张补位卡上标注「补位（非需求驱动）」。
- 依据：`MULTI_MAX=0` 反事实证明引擎**有能力**稳定输出 6 人（18/18），补位不需要新逻辑，只需放宽停止条件。

**G3（参数化，建议）**——把 `MULTI_MAX`（多功能合并上限）从硬编码常量提升为**产品级可配参数**
- 理由：它是规模的一阶杠杆（0→6.0 人、2→5.33、4→3.83），且直接影响「一只多面手能顶几条需求」的策略表达；暴露为参数后，4/5/6 人目标可统一由它单点调节。

**G4（缺陷登记，建议修正）**——`STOP_PRIORITY` 语义/文案
- 现状：`STOP_PRIORITY=1` 时 `need.priority < 1` 不可达（实测 0 次命中），L5165 分支与 UI 文案「剩余最高优先级 < 1 → 立即停手」为**失效描述**。
- 建议：或改为 `priority <= STOP_PRIORITY`（真正生效，阈值 1 即「只剩兜底级需求时收手」），或在常量中引入 0 优先级需求；同时更正文档表述，避免后续误读为「当前会按优先级截断」。

**不建议改动项（记录以免反复）**：`MAX_TEAM=6`（硬上限，8/18 触顶，符合产品预期）、候选池零硬门（`poolForNeed` 全量可见，与用户「反对负向硬排除」的方法论一致）、`needList` selfGate 收窄（L5108-5123，正是防止规模塌到 2–3 的护栏）。

## 9. G1 评估侧登记：规模中性评估口径（v4.8 追加）

> 登记人：A 线（v4.8 产品侧改进，`build_tool_html.py` 实施者）。本节**只登记评估方法论**，不含 HTML 逻辑改动。
> 上游证据：本报告 §3（评测口径分解）、`nn_data\T2.1规模分层复测_报告.md`（M5/G4 判据线，逐层 T2.1 32 格 0 通过、池化规模通道贡献 +0.2634）。

### 9.1 三条口径缺陷（登记）

1. **`--min-size` 过滤影响**：评测池由 `nn_data\g4_pool_build.py --min-size 3` 构造 ⇒ 3 人以下队伍被排除。引擎自身推荐 **min 4 / max 6**（§2.2），故该过滤对引擎方案基本无影响，但它**截断了真实规模分布**，使"平均规模"类结论无法外推到 1–2 人情形；任何规模均值必须在注明下限（≥3）的前提下解读。
2. **均值型指标存在规模偏置**：池化 AUROC/Δ 中，队伍规模与真值胜率强相关（`rho_win_vs_size = 0.7232`，size3 0.1696 → size6 0.7562）。**层间方差混入模型排序力** ⇒ 池化 Δ 的规模通道贡献高达 **+0.2634**（§3.3 / T2.1 §3.1）；平凡规则 `size_only`（纯按人数排序）即可拿到 +0.2992（> 探针 D 的 +0.2401）。**结论：任何"模型优于引擎"的池化声明必须做规模分层或规模配对，否则不可采信。**
3. **采样模式混淆（mode A/B/C/D）**：池中仅 **175/3962 行（4.4%）是引擎原方案（mode A）**；mode B 删人 1556、mode C 换人 1109、mode D 随机组队 1122（§3.2）。D 类随机队规模均值 3.872，直接拉低池均值 ⇒ 「引擎平均 3.60 人」是**口径假象**。

### 9.2 推荐口径（登记，供后续评测线执行）

| # | 口径 | 做法 |
|---|---|---|
| G1-1 | **只用 mode A** | 评估"引擎排序质量"时只用原方案行（175 行），不使用删人/换人/随机扰动行 |
| G1-2 | **或按 mode 分层** | 若必须混合，则按 mode（A/B/C/D）× size 分层报告，禁止池化汇总 |
| G1-3 | **规模分层/配对** | 按 size ∈ {3,4,5,6} 分层（层内规模恒定，消除规模通道），或规模配对的对手池抽样 |
| G1-4 | **报告下限** | 任何规模统计必须注明 `--min-size` 下限与样本量，均值需附分布 |
| G1-5 | **基线对照** | 至少并列 `size_only` 与 `meanBST` 两个平凡基线，防止模型增益被规模通道冒充 |
| G1-6 | **标签口径** | 真值为 battlesim 代理胜率（ER 无对战统计，已知缺口）；换用 size-matched 标注是下一杠杆（T2.1 §6.2） |
