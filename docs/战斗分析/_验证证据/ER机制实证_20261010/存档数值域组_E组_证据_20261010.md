## E1 · `+0x0A` bit9-5「分组N」（招式3 相关，随招式变化但不影响 id 计算）语义

**源码结构证据（权威）**
- `ER-source\nextdex\static\js\load_save.js:131-136`（word6 @ `start+12`，即 A+0x08）：
  ```
  mon.moves[1]  = readBit(word6, 0, 11)   // 招式2, 11 位
  mon.moves[2]  = readBit(word6, 11, 11)  // 招式3, 11 位
  mon.friendship= readBit(word6, 22, 8)   // 友好度, 8 位
  mon.isEventMon= readBit(word6, 30, 1)
  mon.isAlpha   = readBit(word6, 31, 1)
  ```
- 换算：解析器 `+0x0A`（u16，A 相对）= `start+14` = word6 的 **bit16..31**。故：
  `+0x0A bit0..4` = word6 bit16..20 = 招式3 bit5..9（解析器已正确用作 id 高位）；
  `+0x0A bit5` = word6 bit21 = **招式3 bit10（第 11 位）**；
  `+0x0A bit6..9` = word6 bit22..25 = **友好度 bit0..3**；
  `+0x0A bit10..13` = word6 bit26..29 = 友好度 bit4..7；
  `+0x0A bit14` = isEventMon；`+0x0A bit15` = isAlpha。
- ⇒ `+0x0A bit5..9` = `((friendship & 0x0F) << 1) | 招式3_bit10`，**不是独立字段**。

**实档对拍（真值 6/6 命中，决定性）**

| 队伍 | friendship | 实测 +0x0A bit5-9 | 公式 `(fr&0xF)<<1` | 一致 |
|---|---|---|---|---|
| party0 土王Mega | 18 | 4 | (18&15)=2 → 4 | ✓ |
| party1 598 | 10 | 20 | 10 → 20 | ✓ |
| party2 2667 | 42 | 20 | 10 → 20 | ✓ |
| party3 1677 | 19 | 6 | 3 → 6 | ✓ |
| party4 249 | 40 | 16 | 8 → 16 | ✓ |
| party5 882 | 22 | 12 | 6 → 12 | ✓ |

（6 条记录的招式3 实测 id 均 <1024，故 `招式3_bit10 = 0`，字段值完全由友好度低 4 位决定。）

**解析器对照**：`parse_er_save_v4.py:128-138 decode4_moves()`：
`m3 = ((v0A & 0x7FF) & 0x1F) << 5 | (v08 >> 11)` —— 只取 5 位，**丢弃 `+0x0A bit5`（招式3 的第 11 位）**。而 `+0x0A bit5..9` 被 `AGENTS.md:108` 记作「分组N（语义待定）」。

**结论**
1. 「分组N」不存在：该 5 位 = 招式3 最高位 + 友好度低 4 位（+ 更高位是 isEventMon/isAlpha）。
2. 用户观察到的「随招式变化」应来自**跨精灵友好度差异**（6 只队友的友好度 10/18/19/22/40/42 各不相同，字段值随之不同），而非招式变化；同一条记录的「招式3 换招」不会改变这 5 位（其 bit5 只在招式 id ≥1024 时才翻转）。
3. **招式3 应为 11 位**（word6 bit11-21），正确式：`m3 = ((v0A & 0x3F) << 5) | (v08 >> 11)`（`0x3F` 而非 `0x1F`）。

**与引擎/解析器现值是否一致**：**不一致**（语义错标 + 取值位宽少 1 位）。
**影响面（本档实测）**：431 条记录中 **1 条**的招式3 ≥1024（A=0x0CA70，物种 706，招式3=**1027**）→ 现解析器会把 1027 解成 `1027-1024 = 3`（错招）。gameData 中 id ≥1024 的招式共 **8 个（1024–1031）**，故该缺陷可触发。
**状态**：**定稿**（源码 + 实档双证）；修复动作本次未执行（禁改解析器），仅登记。

## E3 · 队伍尾部 `+0x48..+0x4B` u32 待定；PID/加密块 key（`load_save.js: key = OTID ^ personality`）对照

**源码结构证据**
- `load_save.js:124-125`：记录 **S+0** = personality(4B)，**S+4** = otId(4B)。
- 队伍记录步长 76 B（本档实测：6 条队伍记录的 A 间距恒为 76；`parse_er_save_v4.py:107` `find_party()` 亦以 76 为判据）⇒ 下一条记录真起点 `S₂ = S + 76`。

**实档对拍（5/5 命中）**

| 队伍 | u32 @ (A+0x48) | 下一条记录 personality @ (A₂−4) | 一致 |
|---|---|---|---|
| party0 | 0x05A9F22B | party1 = 0x05A9F22B | ✓ |
| party1 | 0x0BCA7587 | party2 = 0x0BCA7587 | ✓ |
| party2 | 0x472DA40B | party3 = 0x472DA40B | ✓ |
| party3 | 0x68CDE768 | party4 = 0x68CDE768 | ✓ |

**与引擎/解析器现值是否一致**：**一致**（解析器未把它当字段，无污染）；`AGENTS.md` 文字登记可关闭。
**状态**：**定稿**。

## E7 · EV 上限（引擎是否应做 252/510 校验）

**源码常量（精确行号）**
- `ER-source\include\constants\pokemon.h:277` `#define MAX_PER_STAT_EVS 252`
- `ER-source\include\constants\pokemon.h:278` `#define MAX_TOTAL_EVS 510`
- `ER-source\include\constants\pokemon.h:279` `#define EV_ITEM_RAISE_LIMIT 252`
  ⇒ **单项上限 252、总量上限 510**（无 255 口径，无「单项 252/总量 510 二选一」的歧义）。

**代码强制（双向）**
- 战斗加 EV：`src\pokemon.c:7066 MonGainEVs()` —— `L7120` `if (totalEVs >= MAX_TOTAL_EVS)`；`L7164-7165` 总量截断到 510；`L7167-7169` 单项截断到 252。计次器 `L7180 GetMonEVCount()`。
- 摘要界面 EV 编辑器：`src\pokemon_summary_screen.c:1983-1987` 与 `L2103-2109` 同时夹住单项 252 与总量 510。
- 其它使用点：`src\field_specials.c:1418`（`GetMonEVCount(...) >= MAX_TOTAL_EVS`）、`src\field_specials.c:5556`（硬编码 `>= 510`）；`battle_dome.c:2470/4490`、`battle_factory.c:442/483`、`pokemon.c:3556/3708/3737` 均以 `MAX_TOTAL_EVS / n` 均分。

**存储形式**：6 × u8（`load_save.js:153-158`：hpEV/attackEV/defenseEV/speedEV/spAttackEV/spDefenseEV，各 1 B；解析器 `parse_er_save_v4.py:346` `rec[0x14:0x1A]`）⇒ **物理可存 0–255**，但游戏逻辑**不会写入 >252 的单项、>510 的总量**。

**实档统计（431 条记录全量扫描）**
- 单项 EV：最大值 **252**；>252 的条数 **0**。出现的取值：0,2,4,6,8,12,32,37,40,64,66,70,108,112,118,124,126,128,130,134,142,144,160,170,188,190,192,232,248,**252**。
- 总量 EV：最大 **510**；>510 的条数 **0**；均值 113.4。分布（Top）：`0×334`、`510×81`、`508×11`、`504×2`、`252×2`、`479×1`。

**结论（定稿口径）**
1. ER 侧合法上限：**单项 ≤ 252 且 总量 ≤ 510**；两者**均为游戏强制**（源码双向夹取）。
2. 253–255 / 总量 >510 只可能来自**改档器/导入工具**，属非法值 ⇒ 引擎应把它们视为「需要注意」而非静默接受。
3. 「引擎不做 510/252 校验」的现状：**存档被游戏保证在合法域内**，因此不做校验不会产生错误读数；但做**建议性校验**（提示而非拦截）可识别改档/异常档。建议口径：`单项 >252` 或 `6 项之和 >510` → 标记「疑似非法 EV（超出 ER 上限 252/510）」。

**与引擎/解析器现值是否一致**：解析器仅直读 6×u8，**无校验**；本定稿建议为**新增建议性校验**（不改读数口径）。
**状态**：**定稿**。

**源码（机制 = 逐物种，非硬编码单一曲线）**
- `src\data\pokemon\experience_tables.h:18` `const u32 gExperienceTables[][MAX_LEVEL + 1]`；8 张表（注释行）：Medium Fast(L20)、Erratic(L123)、Fluctuating(L226)、Medium Slow(L329)、Fast(L432)、**Slow(L535)**、Medium Fast copy2(L638)、copy3(L741)。

  `L7 EXP_MEDIUM_SLOW(n)((6*CUBE(n))/5 - (15*SQUARE(n)) + (100*n) - 140)`；
  `L8 EXP_ERRATIC(n)…`；`L13 EXP_FLUCTUATING(n)…`
- `include\constants\pokemon.h:326-331`：`GROWTH_MEDIUM_FAST 0 / ERRATIC 1 / FLUCTUATING 2 / MEDIUM_SLOW 3 / FAST 4 / SLOW 5`。
- 取值来源：`src\pokemon.c:4044`（`GetLevelFromMonExp`）与 `:4056`（`GetLevelFromBoxMonExp`）：`while (level <= MAX_LEVEL && gExperienceTables[gBaseStats[species].growthRate][level] <= exp) level++;`；建怪 `src\pokemon.c:3392`：`SetBoxMonData(boxMon, MON_DATA_EXP, &gExperienceTables[gBaseStats[species].growthRate][level]);`

**真实存档交叉验证（决定性，431 条）**

  `slow 430 / medfast 0 / medslow 0 / fast 0 / erratic 0 / fluct 0`；唯一不命中 1 条（物种 218 Slugma，exp 156896 —— 位于 `slow(50)=156250` 与 `slow(51)=165813` 之间，属「升级途中累计经验」的正常态）。
  ⇒ **430/431 条 exp 精确落在 `floor(5n³/4)`（GROWTH_SLOW）上，0 条落在任何其它曲线值上**。
- **截图锚定等级对拍**（等级由游戏内截图独立得到）：
  | 物种 | 存档 EXP | Slow 曲线 | 若按 MEDIUM_FAST | 若按 MEDIUM_SLOW |

  | 411 Bastiodon 护城龙 | 58320 | `slow(36)=58320` **精确命中（Lv36）** | `medfast(36)=46656`（L38）✗ | `medslow(36)=40007`（L40）✗ |
  | 469 Yanmega | 58320 | `slow(36)` ✓ | ✗ | ✗ |
  | 741 Oricorio | 640000 | `slow(80)=640000` ✓ | `80³=512000` ✗ | ✗ |

**官方解码器佐证（其等级功能本身不可用）**
- `load_save.js:356-362 curveMap` 以 `gameData.growT[species.stats.grow]` 取曲线名；v2.65 `growT=['']` ⇒ 取不到。
- `load_save.js:363-370 getGEN3expRequired()` **缺 `return`**（`fn(level)` 未返回）⇒ 恒为 `undefined`，`getGEN3level()` 失效（官方 NextDex 自己也无法算等级）⇒ **更不能用它当等级权威**。

**结论**
1. **gameData 的 `species[].stats.grow` 与 `exp` 全 0（1907/1907）、`growT=['']` ⇒ 官方 JSON 不可用**（精确计数已给出）。
2. **ER 的成长机制是「逐物种 `.growthRate` → `gExperienceTables[rate][level]`」**（源码级），**并非硬编码单一曲线**；历史版本 gameData 亦为混合分布（v1.6.1 等）。因此「全物种统一」**不能由源码或历史数据推出**。
3. **但对本验证档（v2.65）而言，实读结论是唯一的**：430/431 条 exp 精确等于 GROWTH_SLOW 值、其余曲线 0 命中、且截图锚定等级与 Slow 曲线逐条吻合。
4. **解析器/引擎现用式 `exp = 1.25·L³` 即 GROWTH_SLOW，对 v2.65 是「正确」的**；**问题在命名**：本项目把该口径写作「medium-slow」是**术语错误**（medium-slow = `6n³/5 − 15n² + 100n − 140`，与实测不符）。
   - 附带澄清：`AGENTS.md:113` 的「Slow 组 Lv=round((EXP/1.25)^(1/3))，Lv100↔1,249,984」——**公式与曲线判定正确**；「1,249,984」是解析器 `exp5*32` 的截断值（`exp5 = exp>>5`，丢掉低 5 位），**真值应为 1,250,000**（见 §10 缺陷 3）。

**与引擎/解析器现值是否一致**：公式 **一致且正确**（就 v2.65 而言）；**标签「medium-slow」不一致，须改为「GROWTH_SLOW / Slow 组」**；**不要**改用 medium-slow 公式。
**风险与建议（不改代码，仅登记）**：若未来解析非 v2.65 存档（或某版本恢复混合曲线），统一 Slow 会使 Lv 偏 1–2；届时可按 `GROWTH_*` 常量 + 6 条曲线宏（`experience_tables.h:4-15`）实现逐曲线换算。
**状态**：**定稿**。
