## 2. 固定章节结构（每篇必须且仅含这 5 节）

### 一、机制说明（ER 实际规则）
- 从本地数据出发给出确切数值与结构，用表格承载（克制表/特性标签表/招式数值表等）。
- 每个机制都要回答"对战场景下意味着什么"，禁止纯数据罗列。
- 本地数据溯源标注（哪个文件哪个字段，如 `ERDATA.matchup[地面][火]=1`、`gameData species[2232].stats.abis`）。

### 二、与原版/常规差异（重要）
- 逐条列出 ER vs 原版/常规对战环境的差异，每条必须给出：差异内容、数据或来源证据、对战含义。
- 已确认事实（沿用，勿改）：火→地面=1x（**原版标准表亦为 1x，无差异**——此前"原版2x"系标准表记忆错误，Bulbapedia/pikapedia/pokemons.io 三证，2026-10-06 更正）；水→电=1x（与原版一致）；天气增伤 20% 非 50%；冻伤替代冰冻；无蛋招/TM 字段、教学池合并；个体默认满但不参与能力公式（IV=0 口径）；4 特性机制。
- 差异未确认的写"待验证"，禁止编造。

### 三、对战决策影响
- 分三个决策场景：**配招**（选什么招/怎么选）、**组队**（选什么精灵/怎么配合）、**对战**（场上怎么用：换人/攻击/防守判断）。
- 每个决策给"决策场景 → 考量因素 → 推荐决策"的推导，而非结论堆砌。

### 四、可执行规则建议（引擎判定规则，全篇核心）
- 开头一段「现状引擎评估」：现有实现是什么（对照 _00_资料汇编 的 C 节）、它的不足、本文档要升级的方向。
- 然后给出规则清单，每条严格按以下格式（可代码化的 IF-THEN）：

```
| 规则编号 | 适用场景 | 判定条件（数据字段级） | 引擎动作 | 建议权重/优先级 |
|----------|----------|------------------------|----------|----------------|
| R02-01 | 特性选择 | 某可选特性带 im 水 且目标精灵 4x 弱水 | 该特性评分 +2 | 高 |
```

- 规则编号 R<篇号>-<序号>；判定条件必须能用现有数据字段表达（如 matchup、types、abis/inns、base、moves 数值、ABI_TAGS 标签）；引擎动作必须明确（加分/过滤/排序/提示）。
- 每篇 ≥10 条。多维度综合（种族+特性+技能+属性+战略），禁止单维排序——这正是用户对旧"纯威力排序"的批评。

### 五、参考资料来源
- 真实 URL + 类型标注（官方wiki / 官方GitHub / 官方数据 / 社区 / 个人 / 本地数据文件）+ 一句话说明该来源提供了什么。
- 本地数据源列文件绝对路径。禁止编造 URL；找不到的主题写"未找到公开资料"。

## 4. 深度与风格要求
- 中文正文每篇 ≥2500 汉字（不含表格/代码块）。
- 术语准确、可溯源；个人推断必须标注"（个人观点）"。
- 用 Markdown 表格、分节标题；不写废话和套话。
- 结论必须与 _00_资料汇编.md、AGENTS.md 已确立结论一致；有冲突时以本地数据为准并在文档中说明。

## 5. 硬约束（违反即退回）
1. 禁止编造：任何 ER 数值必须来自本地数据文件或真实网络来源；任何 URL 必须真实。
2. 禁止停留在数据罗列：每条机制必须有对战含义或决策指导。
3. 规则必须可执行：判定条件能映射到现有数据字段。
4. 不修改任何代码/数据文件；只写自己负责的那一篇文档。
5. 输出到指定绝对路径，文件名一字不差。
