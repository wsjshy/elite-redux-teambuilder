## ⚠️ v4.2 → v4.3 修订说明（方法论的**方向性**修正，必读）

**v4.2 的问题**：把「18 体系 × 6 槽位」写成了**固定骨架**——读起来像「晴天队**就是**：天气手／速攻核心／特盾／物盾／钉子+轮转／补盲」。**这是反模式。**

**用户原话**：那只举例如煤炭龟开晴／妙蛙花速攻／补盲／联防／撒钉／轮转，**不是让定死成模板**。

**v4.3 的正确方向**：

1. **需求驱动动态构建（§4.5）**——队伍先由**核心**及其**暴露出的缺口**决定「需要什么」：**需求类型与数量随核心动态变化，无固定 6 项**；一只可满足多条需求（**多功能价值加分**）；**需求清零即可停手，允许 <6 的紧凑队**。
2. **战术流派推导（§4.6）**——流派是**从输出画像 / 耐久速度画像 / 特性池 / 可学功能招客观推导出的「打法」**（如「晴速攻强化清场」「空间慢速重炮」），**不是**「物攻队 / 特攻队」的二分，也**不是**写死的 18 个标签。
3. **§2 的 18 体系槽位清单保留但降级**为「**需求示例参考库**」（`NEED_EXAMPLES`）：它是「历史上常见于该体系的**需求候选集**」，供引擎**查询与打分**；**不再是必须填满的槽位模板**，其 `Σ n == 6` **不再是校验项**（见 §2.0 降级说明）。

**不变的部分（v4.2 的正确结论，继续有效）**：全部**正向加分制**（不表达为剔除）；§1.4 的 ER 特殊性实证、§3 的 D1–D18 正向维度库、§4.3/§4.4 的伪代码形状、与 01–06 的口径冲突处理（C1–C13）**均继续有效**。**另更正一处**：v4.2 曾写「唯一硬门 = `wxConflict`」，但引擎已按用户裁定**删除该函数**（§1.5 已重写，登记为 **C14**）——**全流程不设硬门**。

**外部依据（`_03` §13）**：Smogon 论坛明确否定「严格角色分配」——"you do not need a special or physical wall, as much as you need **counterplay against specific threats**"（§13.1）；官方文章给出发动机原型「**选 1 只 → 列它的 weaknesses 与 checks/counters → 找覆盖者**」（§13.2）；ER 社区结论落在 "cover **roles** instead of just types"（§13.8）。

## 一、机制说明（ER 实际规则）

### 1.1 为什么组队单位是「槽位」而不是「精灵」

外部资料给出的组队方法学内核高度一致：**先把 6 个位置拆成若干「槽」（角色），再往槽里填精灵**。

> **v4.3 澄清（重要）**：上述「槽」是**需求的可读表达**，**不是前置模板**。外部资料本身即反对把角色写死——见 §13.1 的官方论坛原句。因此本文 v4.3 的正式单位是 **`need`（需求条目）**，「槽（S-ID）」只作为**需求的分类词表**继续使用（§1.3）。

- Smogon 官方论坛版规的原句是 **"To wonder what set to run on a Pokémon is to build without roles."**——「不考虑角色就想配招＝没有在组队」["https://www.smogon.com/forums/threads/teambuilding-guide.3552468/"]。
- ER 社区自身的实战配队表也**不是按属性列、而是按 Role 列**：`Fighting or Fairy attacker | Handles Sidney and gives useful Dark coverage`、`Electric attacker | Handles Wallace's Water-types` 等 6 行槽位["https://romprofessor.com/pokemon-elite-redux/what-are-the-elite-four-and-champion-teams-in-pokemon-elite-redux/"]。
- 社区指南给出的槽位填充**顺序**是固定的四步：**锁体系核心 → 定 1–2 名体系受益打手 → 补控速 → 补「反制对手天气」**["https://pokestats.cc/guides/sun-team-guide"]。

现状引擎（`build_tool_html.py`）已有 `SYS_DIMS`（12 张**体系级**维度权重表：空间/晴/雨/沙/雪/场地/受/强化/吸血/双天气/顺风/通用）与 `tplRecs`（18 套模板推荐），但它们是**「一只精灵在体系里得多少分」**，缺两层：**「这队到底需要什么」（需求层）** 与 **「这只精灵满足哪几条需求」（分配层）**。v4.3 补齐这两层：**需求层 = §4.5**，**分配层 = §4.4 的按需求贪心填充**。

**关键约定（v4.3 修订）**：§2 的槽位清单**不再是必须填满的骨架**，而是**需求示例库**（§2.0）。真正的不变量只有两条：

1. **输出队伍中，每条 `need.satisfy` 求值为真**（或被显式 `defer` 并登记到 `openNeeds`）；
2. **`|team| ≤ 6`**——**允许 <6**（见 §4.5.6 终止条件）。

### 1.4 ER 特殊性对槽位的影响（本任务 ③）

ER 不是原版，**有五处机制差会直接改写槽位表**。

**① 4 特性机制（1 可选池 + 3 天性）→ 设置手槽大开 + 槽内要选「哪条特性」**
`species.stats.abis`（定长 3，n 选 1）与 `species.stats.inns`（定长 3，固定）双池。只读探针实测（`_probe_slots_v42.py`，数据源 `ER-source\gameDataV2.65beta.json`，有效物种 1905）：

| 体系 | 设置手特性 | 经 `abis` 池可达 | 经 `inns` 天性可达 | 并集 |
|---|---|---|---|---|
| 雨 | Drizzle(2) | 21 | 5 | **26** |
| 晴 | Drought(70) | 19 | 4 | **23** |
| 沙 | Sand Stream(45) | 14 | 3 | **17** |
| 雪 | Snow Warning(117) | 24 | 3 | **27** |
| 电场 | Electro Surge(226) | 11 | 5 | **16** |
| 精神场地 | Psychic Surge(227) | 15 | 3 | **18** |
| 青草场地 | Grassy Surge(229) | 26 | 8 | **34** |
| 薄雾场地 | Misty Surge(228) | 9 | 4 | **13** |
| 剧毒场地 | Toxic Surge(834) | 8 | 3 | **11** |

- **气候 4 系并集可达 = 91（4.8%）**，其中**仅靠可选池（战前可切）= 76**、**含天性锁死 = 15**。原版中 `Drizzle/Drought/Sand Stream/Snow Warning` 的持有家族是**个位数~十余个**量级——ER 每系候选**放宽到 11–34 只**。
- **槽位设计含义**：设置手槽的**候选池大幅变宽**（好消息）；代价是**同一只怪可扮演多种设置手**，故槽位决策 = **「选哪只 × 选哪个特性」二维**，不能只选精灵。
- **天性 vs 可选池的确定性差**：`Torkoal` 的 `inns=['Shell Armor','White Smoke','Drought']`——日晒**在天性里、锁死**，是「确定型晴天手」；`Gigalith` 的 `abis=['Loose Rocks','Sand Stream','Solar Power']`——扬沙在**可选池**，需战前选中才成立。**引擎口径**：天性命中 `×1.0`、仅可选池命中 `×0.7`（承接 R06-04 的「潜力 ×0.7」）。

**② 3 天性固定 → 槽位可能被「锁死」或「反噬」**
天性不可更换：若一只怪的天性自带一个**与目标体系对立的天气特性**，它会**顶掉**本队天气。v4.2 起对此**不再硬排除**（`wxConflict` 已按用户裁定从引擎删除，见 §1.5 / **C14**），改为排序**靠后**（引擎 `WX_SYS` + `coreWxKey` / `clash`）。因此槽位表的**必要条件**写「`abis ∪ inns` 不引入对立体系」是**优先项**，但**不得**据此剔除候选。

**③ 双刀 → 破盾槽与清场槽的门槛按双档**
R06-17 口径：双刀门槛 `≥90` 全项，或 `≥70` 但配 4 项加成之一。**槽位含义**：`S-BRK`（破盾槽）优先选双刀，`S-ATK`（速攻槽）优先选单侧极值。

**④ `-ate` 属性转换 → 补盲槽的候选面扩大**
`ABI_ATE` 口径：宏族倍率 ×1.0（三个特殊条目 ×1.1）、`stabConvert`（×1.5，适应力 ×2.0）、`proc 1.0`、共 9 条转换。**槽位含义**：带 `-ate` 的精灵能把**一般系招转成本系**，等价于**多带一个本系打击面**——`S-COVER`（补盲槽）评分额外给 `-ate` 加成（D16），因为它能用「本来不吃本系加成的招」补缺口。

**⑤ Mega / Redux 形态 → 槽位候选按「形态」评估**
形态体系独立 id、独立种族值（例如 `Charizard Mega Y` 与 `Charizard` 是两条记录）。**槽位含义**：
- `S-SET` 的候选要评估**实际使用的形态**：`Charizard Mega Y` 的 `abis=['Drought','Drought','Drought']` + `inns=['Hellblaze','Flash Fire','Solar Power']`——**一只同时是设置手与增伤核**（「天气双核」的单体形态）；
- 形态最终性入评分：`final` 形态 `+2`（承接 `isFinalSp` 与 `evolutions kd==0` 的 640 只非最终形态不推荐口径）；
- Mega/Redux 与 `coreSys` 取并集：**形态也能提供体系特性**，故 `S-SET` 判据对形态同样成立。

### 1.5 不设硬门（**v4.3 更正**：`wxConflict` 已按用户裁定删除）

> **⚠️ 重大更正（v4.3 自检发现，与 v4.2 正文相反）**：v4.2 正文把 `wxConflict` 写作「唯一硬门、保留」；但**引擎已按用户裁定将其删除**（`build_tool_html.py` L2414 / L2584 / L3406 注释 + 偏差登记 **D-1**：「文档 §1.5/§4.4 把 `wxConflict` 列为唯一硬门、保留，**用户本轮明确要求移除硬互斥 ⇒ 以用户指令为准**」）。现引擎中 **`wxSetOf` / `wxConflict` 已不存在**（仅存注释），残留的只有 `WX_SYS` 常量与 `coreWxKey` / `clash` 局部变量。**本文以引擎现状与用户裁定为准**，该分歧登记为冲突 **C14**。

**本文所有评分一律正向加分制**（见 §三），**全流程不设硬门**：

```
WX_SYS = ['晴','雨','沙','雪']                 // 引擎现存常量（L2415）
coreWxKey = coreSys(core) ∩ WX_SYS             // 核心的天气键（场地不计入冲突）
clash(s)  = (coreSys(s) ∩ WX_SYS 与 coreWxKey 有交集) 且 (≠ coreWxKey)
```

**含义**：纯晴队的候选若自带扬沙/降雨/降雪，**只被排到后面（`clash` → `fit` 排序键下调），不被剔除**——候选池保持全量可见（引擎侧实证：`recs.pool` **725 只全量计分**；「龙头地鼠在空间队低排位可见、未被剔除」是用户铁律）。**因此**：任何「据此排除候选」的写法都属违规；引擎 `fit` 键中 `fit = 0`（自带另一套**天气**；场地不冲突）正是这一软化的落地。

### 3.3 正向化改写规则（承接本任务②「不表达为剔除」）

现行 `SYS_DIMS` 与 06 §4.2.3 的补位树里有**负分与硬排除**（如 `属性完全重复 −2`、`主定位重复 −1`、`力度不足 −3`、`速度 >85 硬排除`）。**本文一律改写为「正向加分 + 必要条件」两段式**，使评分只做加法：

| 原（负向 / 剔除） | 现（正向 / 门） | 说明 |
|---|---|---|
| 属性完全重复 `−2` | 属性与全队两两不同 `+1`（D18） | 重复不再扣分，只**不加多样性分** |
| 主定位重复 `−1` | 与队内主定位互补 `+1` | 同上 |
| 力度 `< 95` → `−3` | 力度达标 `+2/~+5`，未达标 `0` | 未达标只是拿不到分 |
| 耐久 `< 280` → `−2` | 耐久达标 `+3`，未达标 `0` | 同上 |
| 空间「速度 `>85` 硬排除」 | `S-TRUSE` 的**必要条件** = `base[spe] ≤ 85` | 角色定义 ≠ 评分；不会给任何候选负分 |
| ~~`wxConflict` 硬排除~~ | **已删除**（v4.2 用户裁定移除体系硬互斥；见 §1.5 / **C14**） | 现改判为「对立天气仅排序靠后」的**软规则** |

**结果**：任一候选在某槽位的得分**恒 `≥ 0`**；「不适合」表现为**分数低**或**过不了角色门**，而非被扣分或剔除——这既满足用户要求，也让引擎的排序逻辑保持单调可解释。

```
function buildTeam(input):
    core   = input.core                              # v4.3 真正入口：一只核心
    sysKey = archOfSp(core) || archOfTpl(input.target?.template) || '通用'
    size   = input.target?.size ?? 6                 # 上限，不是必须值

    # ---- 阶段 0：候选池与体系先验（**不设硬门**，§1.5 / C14）----
    cand = pool.filter(s => isFinalSp(s) || isMega(s))     # R07-04
    cand.forEach(s => s.fit = clash(s) ? 0 : s.fit)        # R07-03：对立天气仅排序靠后（**不 filter**）

    # ---- 阶段 1：由核心生成需求清单（v4.3 主流程，见 §4.5）----
    needs = genNeeds(core, cand, input.constraints)         # R07-23 ~ R07-29
    team  = [core]
    needs = applyExisting(needs, core)                      # 核心自身能满足的先置 satisfied

    # ---- 阶段 2：逐条满足需求（**不是**「按槽位顺序填」）----
    while not shouldStop(team, needs, input.budget).startsWith("STOP"):    # §4.5.5
        need   = topOpen(needs)                             # 最高优先级未满足需求
        pool_i = [s for s in cand if needSatisfied(need, s)]           # 求值器白名单 §4.5.1
        for s in pool_i:
            s.score = Σ_d ( pts_d(s, need) * w_d ) * cert(s, d)        # §3.1/§3.2 正向加分
                    + 1.0 * sysDimPrior(s, sysKey)                     # R07-01 体系先验
                    + MULTI_ROLE_BONUS * (multiHits(s, needs) - 1)     # R07-27 多功能价值
        pick = topK(pool_i, 1)[0]
        team.append(pick); cand.remove(pick)
        needs = consume(needs, pick)        # 已满足项移出；**清零即停 → 可输出 <6 紧凑队**

    # ---- 阶段 3：流派推导（v4.3，见 §4.6）----
    styles = derivePlaystyles(team, needs)                  # R07-30 ~ R07-36

    return { "core": core, "systemKey": sysKey, "team": team, "size": len(team),
             "needs": needs, "openNeeds": openOf(needs),
             "needCoverage": satisfiedOf(needs) / max(1, totalOf(needs)),
             "stopReason": shouldStop(team, needs, input.budget),
             "playstyles": styles.styles, "breakingRoute": styles.breakingRoute }
```

**契约要点（引擎实现时的三个硬约束）**

1. **`Σ n` 不再是架构不变量**：`NEED_EXAMPLES`（§4.3）只是**示例候选集**；需求条目数与队伍规模**随核心动态变化**，**合法输出可为 4~6 只**（`shouldStop` 判定）。引擎**禁止**用 `assert Σ n == 6` 校验。
2. **评分恒非负**：每一分项 `pts ≥ 0`（§3.3 正向化改写），排序单调可解释；「不适合」＝低分或过不了求值器。
3. **零硬门**：全流程**没有任何**排除式过滤（v4.2 用户裁定；§1.5 / **C14**）；对立天气只下调 `fit` 排序键，其余全部是正向加分或求值器判定。

### 4.5 需求清单生成规则（**v4.3 新增 · 引擎主流程**）

> **本节是 v4.3 取代 v4.2「固定骨架」的主入口。** v4.2 的入口是「选模板 → 取骨架」；v4.3 的入口是「**给核心 → 生成需求**」；§2 的示例库降为**候选库**。
> **外部依据**：`_03` §13.1（否定严格角色分配）、§13.2（「选 1 只 → 列弱点与 check/counter → 找覆盖者」）、§13.5（"start with a win condition, add the support it needs, then patch the holes"）、§13.6（一只能担多职 + 5 只收尾合规）。

#### 4.5.1 需求条目结构（Need Item，字段级）

```json
{
  "id": "N-03",
  "desc": "对「火系高速威胁」的答案",
  "kind": "threat",
  "trigger": { "from": "profile", "ref": "core.bulk" },
  "satisfy": {
    "any": [
      { "field": "stats.types", "op": "resistsVs", "value": "火" },
      { "field": "learn", "op": "hasPriorityVs", "value": "火" }
    ]
  },
  "priority": 4,
  "status": "open",
  "satisfiedBy": []
}
```

- `kind ∈ { profile, threat, function, speed, coverage, field, glue }`。
- `satisfy` 是**可求值的布尔表达式**（支持 `all` / `any` / `not` 嵌套），**每个叶子必须映射到现有数据字段**。
- `priority ∈ 1..5`（5 最高），由 `trigger` 基础档 + `multiRoleBonus` 得出。
- `status ∈ { open, satisfied }`；`satisfiedBy` 可含**多只**（多只共同满足一条需求是合法的）。

**可执行性硬要求（否则该需求不得入列）**：`satisfy` 的叶子只能取下列**已验证存在**的求值器。

| 类别 | 允许的求值器（全部为现有符号 / 字段，**已逐一核对存在**） |
|---|---|
| 属性与数值 | `stats.types`、`stats.base`、`bstI`、`bulkOf`、`spdOf`、`atkBest`、`stabBest`、`bestPowOf`、`defCellTrio`、`coreSide` |
| 特性 | `s.stats.abis`、`s.stats.inns`、`isAbilSet`、`abiTagOf`、`SYS_MAP`、`SYS_SET` |
| 招式（**按 id**） | `learnOf(s)`、`hasAny`、`FUNC_MV.{hazard, removal, pivot, speed, rec, protect, wear, weather, boost, boostSpec, boostPhys}` |
| 招式（**按名**） | `learnHasName`、`countLearnNames`、`SYS_MV_KEYS['<主题>']`（主题 ∈ 晴 / 雨 / 沙 / 雪 / 空间 / 强化 / 吸血 / 顺风 / 受 / 双天气） |
| 体系 | `coreSys`、`archOfTpl`、`archOfSp`、`SYS_DIMS`、`WX_SYS`（**注**：`wxConflict` / `wxSetOf` 已删除，**不得**再作求值器引用；对立天气请用 §1.5 的 `clash` 软规则） |

> **口径校正（v4.3 自检发现，两条硬约束）**：
> 1. **引擎中不存在 `spaBest`**。取「特殊侧最高威力」须用 `stabBest(s,'特殊')`（物理侧 `stabBest(s,'物理')`）；「双刀」判定用 `coreSide(s) === '双刀'`。
> 2. **`SYS_MV_KEYS` 是按「体系/主题名」索引的对象**，值是该主题的**招名数组**（已确认键：`晴 / 雨 / 沙 / 雪 / 空间 / 强化 / 吸血 / 顺风 / 受 / 双天气`）。故**不存在** `SYS_MV_KEYS.boost` 这类子键；取「强化招」须写 `FUNC_MV.boost` 或 `SYS_MV_KEYS['强化']`。
> 3. **id 与名不可混用**：`FUNC_MV.*` 与 `SYS_MV_KEYS` 的值分别是**招式 id** 与**招式名**——前者配 `hasAny(learnOf(s), ...)`，后者配 `countLearnNames(s, ..., learnOf(s))`。

#### 4.5.2 `profileOf(core)`：五张画像（全部用现有符号）

| 画像 | 取值（现有符号，**已逐一核对存在**） | 生成的需求方向 |
|---|---|---|
| 输出画像 | `bestPowOf(s, side, conv)`、`atkBest(s)`、`stabBest(s,'物理'/'特殊')`、`coreSide(s)`（→ `物理`/`特殊`/`双刀`） | 力度不足 → 「破盾手」；力度足够 → 「清场手 / 先制收割」 |
| 耐久画像 | `bulkOf(s)`、`defCellTrio(s, at)` | 够厚 → 可承担「站场 / 消耗」；纸糊 → 「联防 / 掩护」 |
| 速度画像 | `spdOf(s)`（= `bstI(s,5)`） | 高速 → 「补盲 / 先制」；低速 → 可走「空间」 |
| 特性池 | `s.stats.abis ∪ s.stats.inns`、`isAbilSet`、`abiTagOf`、`SYS_MAP`、`SYS_SET` | 含设置手 → 「窗口类需求」；含受益特性 → 「体系受益需求」 |
| 功能招 | `hasAny(learnOf(s), FUNC_MV.{hazard, removal, pivot, speed, rec, protect, wear})`；强化招另取 `FUNC_MV.boost` 或 `SYS_MV_KEYS['强化']` | **已具备的功能不再生成需求**（这是「省槽」的来源） |

**`profileOf` 的定义（伪代码；本规格自定义，非引擎符号）**

```js
function profileOf(s):
    sp = stabBest(s, '特殊')            // 现有符号
    ph = stabBest(s, '物理')            // 现有符号
    return {
      role:     classifyRole(spdOf(s), bulkOf(s)),    // → R07-23
      power:    bestPowOf(s, coreSide(s), null),
      fast:     spdOf(s) >= SPEED_HIGH,
      slow:     spdOf(s) <= SPEED_LOW,
      bulky:    bulkOf(s) >= BULK_HIGH,
      mixed:    coreSide(s) === '双刀' || (ph >= MIXED_OK && sp >= MIXED_OK),
      field:    coreSys(s),                            // 现有符号：返回该怪特性所属体系键数组（可空）
      hasBoost: hasAny(learnOf(s), FUNC_MV.boost) || countLearnNames(s, SYS_MV_KEYS['强化'], learnOf(s)) > 0,
      hasPass:  learnHasName(s, '接棒'),
      pivots:   hasAny(learnOf(s), FUNC_MV.pivot),
      hazards:  hasAny(learnOf(s), FUNC_MV.hazard),
      removal:  hasAny(learnOf(s), FUNC_MV.removal),
      rec:      hasAny(learnOf(s), FUNC_MV.rec)
    }

function classifyRole(speed, bulk):
    if bulk >= BULK_HIGH and speed <= SPEED_LOW: return "受队核心"   // 兼可为空间手
    if bulk >= BULK_HIGH:                        return "肉盾核心"
    return "速攻核心"                                              // 含高速与中速
```

> 阈值 `SPEED_HIGH / SPEED_LOW / BULK_HIGH / MIXED_OK` **必须可配置**（建议初值 `100 / 60 / 300 / 同库分位`），**禁止把魔数写进算法正文**；须与 §1.2 的口径表阈值一致。

#### 4.5.3 生成算法（伪代码，可编译级自洽）

```
function genNeeds(core, pool, constraints):
    needs = []
    prof  = profileOf(core)                     # ← 4.5.2 五张画像

    # ① 画像类需求：核心自己的短板
    needs += needsFromProfile(prof, core)        # ← 4.5.3 四配方

    # ② 点名类需求：核心打不过的环境威胁 → 要「答案」
    for t in topThreats(core, constraints.meta):
        needs.push({ id: mkId(needs), kind: "threat",
                     desc: "答案：" + name(t),
                     satisfy: { any: [
                        { field: "stats.types", op: "resistsVs",   value: typeOf(t) },
                        { field: "learn",       op: "hasPriorityVs", value: typeOf(t) },
                        { field: "stats.base",  op: "outSpeeds",   value: t } ] },
                     trigger: { from: "core", ref: name(t) },
                     priority: 4, status: "open", satisfiedBy: [] })

    # ③ 窗口类需求：仅当核心自带天气 / 场地 / 空间时才生成
    if prof.field.length > 0:                          # coreSys(s) 返回体系键数组
        needs += needsFromField(prof.field, prof)     # R07-25

    # ④ 通用需求（低优先，缺位才保留）
    needs += genericNeeds(prof)                        # 出钉 / 清钉 / 控速 / 状态吸收

    # ⑤ 去重合并
    needs = mergeNeeds(needs)                          # R07-28

    # ⑥ 多功能价值：核心已能满足的条目直接置 satisfied
    needs = applyExisting(needs, core)

    # ⑦ 排序
    for n in needs:
        n.priority += multiRoleBonus(n, core)          # R07-27
    return sortByPriorityDesc(needs)
```

**四条核心配方（`needsFromProfile`；全部是「候选」，数量不固定）**

```
function needsFromProfile(prof, core):
```

#### 4.5.5 终止条件（关键：**允许 <6 的紧凑队**）

```
function shouldStop(team, needs, budget):
    if allSatisfied(needs):   return "STOP_ALL_NEEDS_MET"    # 需求清零 → 可 <6
    if len(team) >= 6:        return "STOP_SIZE_LIMIT"
    if budget.exhausted:      return "STOP_BUDGET"
    if noProgressLastK(team): return "STOP_NO_PROGRESS"
    return "CONTINUE"
```

- **需求清零 → 立即停手**，输出**紧凑队（4~6 只）**；这是**合规结果**，不是失败。
- 满 6 只但仍有 `openNeeds` → **输出警告，不自动补齐**（交用户决定）。
- 外部依据：`_03` §13.6 —— "As you see the 2nd team as **only 5 mons yet**, which might be the case of **any team built following these steps**."

### 4.6 战术流派推导规则（**v4.3 新增**）

#### 4.6.0 定义与红线

- **流派 = 打法**：从**客观画像**推导，用于向用户解释「**这支队伍怎么赢**」。
- **三条红线**：① 命名**不得**用「物攻队 / 特攻队」这类**物特二分**；② **不得**写死 18 个标签（体系是**可用元素**，不是队形）；③ **双刀只是破盾路线之一**，**不默认成为第三条流派**（R07-35）。

#### 4.6.1 推导输入（四张客观画像）

| 画像 | 取值（现有符号） | 供给哪些流派 |
|---|---|---|
| 输出画像 | `bestPowOf(s)`、`atkBest(s)`、`stabBest(s,'物理')` 与 `stabBest(s,'特殊')`；双刀可行性 = `coreSide(s) === '双刀'` 或两者**双达标** | 速攻压制 / 双刀破盾 / 空间重炮 |
| 耐久速度画像 | `bulkOf(s)`、`spdOf(s)`、`defCellTrio(s)` | 站场强化 / 受队消耗 / 空间重炮 / 速攻压制 |
| 特性池 | `s.stats.abis ∪ inns`、`SYS_MAP`、`SYS_SET`、`abiTagOf` | 天气增伤轴 / 场地控制轴 / 免疫减伤轴 |
| 功能招 | `hasAny(learnOf(s), FUNC_MV.{hazard, removal, pivot, speed, rec})`、`SYS_MV_KEYS['受']` / `['强化']` | 钉子消耗 / 游击轮转 / 强化接力 |

#### 4.6.2 流派候选池（**打法命名，非物特二分**）

| 流派名（打法） | 触发画像（正向） | 备注 |
|---|---|---|
| 速攻压制 | `spdOf ≥ 高线` 且 `bestPowOf` 达标 | 速度优先 |
| 强化清场（战术） | `FUNC_MV.boost`（或 `SYS_MV_KEYS['强化']`）命中 且 `bulkOf` 够站场 | 需「掩护位」需求配合 |
| 空间慢速重炮 | `spdOf ≤ 低线` 且 `bestPowOf` 高，且队内含空间手 | 与空间体系耦合 |
| 钉子受队消耗 | `bulkOf` 高、`FUNC_MV.hazard` 命中、`FUNC_MV.rec` 命中 | 消耗型 |
| 游击轮转补盲 | `FUNC_MV.pivot` 命中；速度中/高 | 轮转收益 |
| 强化接力轴 | 含接棒类招式 且 队内有强化手 | 组合型 |
| 天气增伤轴 | `SYS_SET` 命中的设置手 或 `SYS_MAP` 命中的受益特性 | 与窗口需求联动 |
| 场地控制轴 | 场地设置手 或 场地相关特性 | 同上 |
| 免疫减伤轴（防守） | `abiTagOf` 命中免疫 / 减伤类 | 防守型 |
| 双刀破盾 | `coreSide(s) === '双刀'`（或 `atkBest` 与 `stabBest(s,'特殊')` **双达标**） | **破盾路线之一**，见 R07-35 |

#### 4.6.3 推导算法（伪代码）

```
function derivePlaystyles(team, needs):
    styles = []
    prof   = aggregateProfile(team)          # 队级画像：对四张像取并集 / 计数

    # ① 输出侧
    if prof.fastCount >= 2 and prof.powerOK:
        styles.push({ name:"速攻压制", score: s1 })
    if prof.hasBoost and prof.bulkOK:
        styles.push({ name:"强化清场（战术）", score: s2 })
    if prof.hasPass and prof.hasBoost:
        styles.push({ name:"强化接力轴", score: s3 })
    if prof.slowCount >= 2 and prof.powerOK and prof.hasTRSetter:
        styles.push({ name:"空间慢速重炮", score: s4 })

    # ② 防守 / 消耗侧
    if prof.bulkHigh and prof.hasHazardMove and prof.hasRecovery:
        styles.push({ name:"钉子受队消耗", score: s5 })

    # ③ 节奏侧
    if prof.pivotCount >= 2:
        styles.push({ name:"游击轮转补盲", score: s6 })

    # ④ 机制侧
    if prof.hasWeatherSetter or prof.hasWeatherAbuser:
        styles.push({ name:"天气增伤轴", score: s7 })
    if prof.hasTerrainSetter or prof.hasTerrainAbility:
        styles.push({ name:"场地控制轴", score: s8 })
    if prof.immuneCount >= 2:
        styles.push({ name:"免疫减伤轴（防守）", score: s9 })

    # ⑤ 破盾路线：互斥择优（双刀只是其中一条，绝不与其它并列叠加）
    routes = []
    if prof.hasBoost:  routes.push("强化")
    if prof.mixed:     routes.push("双刀")
    if prof.hasKnockMove:  routes.push("拍落削道具")
    if prof.bulkHigh:      routes.push("消耗磨血")
    breakingRoute = bestByScore(routes)

    return { styles: topN(styles, 2, 4), breakingRoute: breakingRoute }
```

#### 4.6.4 命名规则

1. **公式**：`[机制前缀] + [打法]`。例：`晴` + `速攻压制` → **「晴速攻强化清场」**；`空间` + `慢速重炮` → **「空间慢速重炮」**；`钉子` + `受队消耗` → **「钉子受队消耗」**；`游击` + `轮转补盲` → **「游击轮转补盲」**。
2. **必须描述打法（怎么赢）**，不得描述属性构成——**禁止**「物攻队」「特攻队」「双刀队」作为流派名。
3. 前缀只用**机制名**：天气 / 场地 / 空间 / 顺风 / 钉子 / 强化 / 接棒 / 免疫。
4. `2 ≤ 流派数 ≤ 4`；不足 2 时按「**主力输出 + 主要防守手段**」兜底命名。

#### 4.6.5 规则表（R07-30 ~ R07-36）

| 规则编号 | 适用场景 | 判定条件（数据字段级） | 引擎动作 | 优先级 |
|---|---|---|---|---|
| R07-30 | 输出侧流派 | `prof.fastCount ≥ 2` 且 `bestPowOf` 达标 | 推「速攻压制」 | 高 |
| R07-31 | 强化侧流派 | `FUNC_MV.boost` 命中 且 `bulkOf` 够 | 推「强化清场（战术）」 | 高 |
| R07-32 | 空间侧流派 | `spdOf` 低者 ≥ 2 且队含 `learn ∋ 433` | 推「空间慢速重炮」 | 中 |
| R07-33 | 消耗侧流派 | `bulkOf` 高 且 `FUNC_MV.hazard` 与 `FUNC_MV.rec` 均命中 | 推「钉子受队消耗」 | 中 |
| R07-34 | 轮转侧流派 | `FUNC_MV.pivot` 命中 ≥ 2 只 | 推「游击轮转补盲」 | 中 |
| R07-35 | **破盾路线择优** | `coreSide(s) === '双刀'`（或 `atkBest` 与 `stabBest(s,'特殊')` 双达标）才生成「双刀破盾」 | 与「强化 / 拍落 / 消耗」**互斥择优，只取 1 条**；**不默认生成** | 中 |
| R07-36 | 流派数量与命名 | `styles.length ∈ [2, 4]` | 若 > 4 取 `score` 前 4；命名按 **4.6.4**（**禁止物特二分**） | 高 |
