## 二、五条判断

### 2.1 单文件 2 MB 不是技术债，是产品需求 —— **不拆**

76.6% 的体积是逻辑代码，数据已经外置成 3 个分片。目标能力是「双击打开即用 / gh-pages 静态部署 / 手机端可访问」，拆成 ES 模块会同时破坏这三条（`file://` 下模块有 CORS 限制）。**拆分收益（可维护性）小于成本（部署与离线性回归）**。这个决定是对的，且已经被 195 个版本的实践验证。

### 2.2 真正的债务是后处理链的「顺序耦合」—— **不动代码，补契约文档**

**现象**：55 个补丁块串在 `deriveBuilds` 尾部，插入位置只能是「末尾追加」。想改中间某块的判据，必须重新验证它下游全部 55 块对字段的假设。

**为什么风险可控**：近期 5 个版本（v4.389→v4.396）的块都写成了「读 `b` 终态 + 只写自己的 `b._vXXX` 字段 + 自包 `try/catch`」，等价于**可并行的层**；真正危险的是 v4.3xx 时代的**原地改写**块（如 v4.390 直接撤掉 v4.389 加进去的第三档）。已经踩过的坑集中在那一层，不在最近这层。

**建议**：不动任何代码，补一份《引擎后处理链顺序契约》—— 逐块登记「读哪些字段 / 写哪些字段 / 是否幂等」，插新块时先查表，能并到尾部就并，必须插队时才做全链复跑。成本约 1 小时，收益是让这条链从「只有作者知道的隐式顺序」变成「可查的显式契约」。**这是本次审视唯一推荐的动手项。**

### 2.3 390 个空 catch 已封顶 —— **不清理，只守住不再增长**

空 catch 占 42.5%，是 v4.1xx 时代「防崩」策略的遗留。它们的真实代价不是代码难看，而是**诊断性丢失**：运行时抛错被静默吞掉，门禁数字不变但行为已错（v4.38x 的 `CONS_ITEM` 静默中止事故就是这么来的）。

但清理要逐个验证「去掉 catch 后是否真的不抛」，等于对 390 个点各跑一次全库回归 —— 收益是诊断性，风险是全库行为漂移。**决定：不清。** smoke 的 `n > 390 throw` 已经把它锁死，新增块一律 `catch(eX){eX.name}`，这就够了。

### 2.4 197 KB 内联 `familyGraph` 是唯一明确可优化项 —— **建议不做**

第 4 段是一行 197,555 B 的 `if(typeof ERDATA!=='undefined'){ERDATA.familyGraph={...}}`（家族谱系：prev/next/mega/prim/form/base）。它**完全静态**，且与外置分片体系（lite/species/adv）的边界不一致 —— 是数据里唯一的例外。

外置后 index 可减 9.5%。但代价是：多一次请求、加载器要改、gh-pages 白名单加第 4 个分片、部署核验从「四文件」变「五文件」、离线单文件场景多一个依赖。**收益是体积，而体积在首屏不是瓶颈（它是数据不是代码，且已有分片并行加载）**。**决定：不做**，除非出现真实的手机端加载证据。

### 2.5 三个 400+ 行巨型函数 —— **不拆，但标注为高风险改动区**

`_deriveBuildsCore`(674) / `guardSubarea`(511) / `_v389SetNat`(495)。拆分的直接后果是**破坏字节级补丁纪律**：现有的补丁锚点全是这些函数体内的唯一字符串，一旦挪动文本，锚点全部失效，后续所有补丁都要重新找锚点。而拆分的收益（可读性）对一个已经稳定运行、每版靠 12 个断言兜底的系统来说，几乎为零。

**决定：不拆。** 但在 `engine-map.md` 里把这三个标成「改动高风险区」，提示改动前先跑全量断言。

## 三、明确不做的事（附理由）

| 不做 | 理由 |
|---|---|
| 拆模块 / 引入构建链 | 破坏 `file://` 可用性与部署简单性，195 个版本的实践证明单文件可行 |
| 引入前端框架（React/Vue） | 现有渲染是事件委托 + 字符串拼装，4205 张卡的重算靠引擎层缓存解决，不是 UI 层瓶颈；换框架等于全量重写 UI |
| 批量清理 390 个空 catch | 逐点验证成本极高，收益仅为诊断性 |
| 拆巨型函数 | 破坏补丁锚点，收益为零 |
| 外置 `familyGraph` | 体积非瓶颈，改动链风险大于收益 |
| 统一 10 个重名回调 | 闭包隔离，无实际冲突，改名反而可能撞名 |

## 四、这次审视真正换来的东西

1. **一条可查的结论**：项目不需要架构重构，需要的是把「隐式顺序」文档化。这避免了下一轮「要不要重构」的重复讨论。
2. **一个封顶指标**：空 catch 390 = 上限，任何新增静默 catch 都会让 smoke FAIL。这是唯一一个「不会恶化」的负向指标。
3. **一个 2.3% 的死代码率**：1184 个函数只有 27 个疑似孤立，说明历次清理（v4.31 去术语、v4.140 统一 helper、v4.336 答案卡重构）是有效的，不是「越改越乱」。
4. **唯一推荐的下一步**：写《引擎后处理链顺序契约》（见 2.2）。

## 五、方法与局限

- **死代码判定用「全文件出现次数 ≤1」**，无法识别通过字符串/eval/事件属性名调用的函数 —— 27 个里有假阳性可能（如 `loadFromHash` 可能经 `window.onhashchange = 'loadFromHash()'` 字符串绑定）。若要精确，需做运行时覆盖率，成本远高于本次审视目标。
- **函数长度是「到下一个 `function` 起点」的近似**，不是大括号配对结果；对嵌套函数会低估外层。
- **没有测运行时性能**：本次只做静态结构审视。性能问题（首算 3~4 秒的体检卡）已在 v4.325 用「占位 + 空闲预热 + 缓存」处理，不在本次范围。
