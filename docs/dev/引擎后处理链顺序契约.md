# 引擎后处理链顺序契约

**生成方式**：`python tools/headless/contract_map.py`（覆盖写本文件）。行号会随补丁推移，**以表为准、以脚本重跑为准**。
**引擎版本**：v4.397

## 一、这份契约解决什么

流派生成末尾是一串**顺序 `try` 块**（`_deriveBuildsCore` 里，`return out` 之前）。每块做一件事：改名、换道具、重算 EV、对齐角色。问题在于**「谁必须在前、谁必须在后」只写在行号里** —— 没有一处文字说清，加新块时只能凭感觉挑插入点。

这不是重构问题，是**契约缺失**：单文件结构不动，只需要把已有顺序写成一张可核对的表。

本次扫描分三档：全文件 **575 个 `catch(eX)`**（含数据层、渲染层等其他位置的 try），其中落在流派生成后处理链内、且操作卡对象的 **127 个**，再筛出**真正会改卡面的 51 个**（下表）。剩下的后处理块是只读判定（如 `eP` 重复 6 次的「是否输出向」小判定），不改数据，插在哪都不影响结果。

## 四、四条硬顺序（写新块前必须核对）

### 1. 名字必须先生成，EV/角色才能跟着算

`roleTag` 只有两个写者：`eV4393`(L18343, v4.393) 与 `eV4394`(L18398, v4.394)。两者都做同一件事 —— **按当前名字重算 roleTag，再用新的 roleTag 重算 EV 与性格**。

这意味着它们**必须排在所有改名字的块之后**。名字写者链共 13 块，最后一个 `eV4392`(L18284, v4.392) 在它们之前 —— 顺序正好成立。

**反例（如果顺序反了会怎样）**：先在 L18000 算 roleTag，再在 L18284 把名字从「骚扰消耗」改成「强化清场」—— 则卡面显示「强化清场」而 EV 仍按消耗位配。这正是 v4.392 之前 `#1 妙蛙种子` 的状态：名字与配置两套逻辑。

### 2. 同名不同块的改名必须首尾相接，不能并行

`eV4391`(v4.391 主力输出压制降档) → `eV4392`(v4.392 骚扰消耗落词) → `eV4394`(v4.394 强化清场名实) 三块**串联依赖**：后一块判断的是前一块改完的名字。

具体例子：`#3 妙蛙花[2]` 原名「强化清场」，v4.394 按「招组里有没有强化招」重算 → 落「主力输出压制」；而「主力输出压制」又要过 v4.391 的火力门（≥95）。**若两块顺序互换，它就永远过不了门**（先过门时名字还不是那个名字）。

### 3. 道具链是「逐块覆盖」，最后写者赢

`it` 有 **21 个写者**，是全库最长的覆盖链。后来的块可以合法推翻前面：`e7`(v4.38 机制必需件保护) 之后的 `eIt1`/`eLk`/`eIL` 仍会覆盖，因为它们的判据更具体（特性×道具死联动）。

**新增道具块的位置规则**：如果它判的是「更具体的联动」，追加到链尾即可；如果它判的是「通用兜底」，必须插在 `eNA`(L13461) 附近靠前 —— 否则会盖掉后面所有具体判定。

### 4. 跨字段块是最大风险点

有两个块同时写多个字段，改它们等于同时动两条链：

| 块 | 行号 | 同时写 | 风险 |
|---|---|---|---|
| `eV4384` | L17875 | 道具 + 名字 | 换道具后名字跟着变（「增伤清场无来源归门」），改一侧就名实分离 |
| `eV4389` | L18162 | EV + 名字 + 性格 | 三者一起重算，改任一处会打破另两处的配套 |

## 五、纪律（写新补丁时照抄）

1. **只改名字的块 → 追加在 `eV4392`(L18284) 之后、`eV4393`(L18343) 之前**，这样 roleTag/EV 会自动跟上。
2. **只改道具的块 → 按「具体联动追加链尾 / 通用兜底靠前」判断**，判不准就追加链尾（宁可少覆盖，不可误覆盖）。
3. **同时改名字又改配置的块 → 必须放在 `eV4393` 之前**，并自己重算 roleTag（照抄 `eV4393` 的 `_v393clean` 零矛盾校验）。
4. **不要在两个块之间插入只读判定块以外的代码**：判定块（只读不改）插哪都安全，改数据的块必须按上表定位。
5. 新增块一律 `catch(eX){eX.name}`，**不得新增空 catch**（smoke 阈值 390 已顶满）。

## 六、怎么验证插入没改变行为

契约本身不产生证据，**零漂移快照才是**：

1. 改前生成全卡快照（`tools/headless/snap_*.js`，six + empty 共 9850 张）。
2. 插入/移动块后重跑同一脚本，逐卡逐字段比对。
3. **差异必须 0**，否则说明插入点改变了某张卡的结果 —— 那就是顺序契约被破坏了。

v4.397（id 表收口 31 处）就是用这个方法证明「纯等价替换」的：9850 张卡差异 0、顺序一致。
