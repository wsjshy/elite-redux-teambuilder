# v4.417 设计 · 队伍意图锚点 + 缺陷重分级 + 最小改动（2026-11-21）

## 0. 立项：用户提出的根本性质疑

用户原话要点：

> 一个个点致命缺陷，最后剩下的到底是最优解，还是趋同化严重的模板？有时候缺点不一定非要解决，也可以通过其他手段解决。HO 队伍每个都脆皮，但靠超强火力打穿。是不是要有一个**最小改动原则**——不喜欢逐个按推荐，最后变成同一套模板、没有联动和区分。比如明显想走雨天，按推荐一个个替换，最后变成四不像。

这不是某个判定算错，而是**建议生成哲学**的问题：当前把每条缺陷都当成「待修复项」，且修复手段不分轻重。

## 1. 现状取证（已用真实队伍验证）

### 1.1 代码事实

- 体检核心 `_teamCheckHtmlCore`（L9001）是 15+ 条**上下文无关的绝对规则**，每条产出严重度 0/1/2；严重度 2 即「硬伤/致命」。
- 修复分两类：
  - 内联「怎么修」长文案：多为换招/换道具/EV/性格（相对温和）。
  - 候选清单 `_tcFixHtml`（L8789）：**全图鉴扫描 + 成员替换**，按钮 `tcApplyCand` 直接换将。
- 换掉谁由 `_tcDropOf`（L8248）决定：对每只算「移除后剩余 5 只的通用聚合分」`_tcAgg`（弱点超标数/岩钉均值/快攻数/最高速），取移除后分最高者。**该逻辑不认识战术体系**。

### 1.2 雨天队实测（6 只全为水系/雨相关）

- 唯一硬伤：**「弱点超标：电×6、草×6」**。但电/草弱点是**水系雨天队的固有组成**——雨天队靠「悠游自如速度先手秒掉草/电、免疫/引水/避雷针队友、先制」来处理，而不是删掉水系。按硬伤建议「分散属性/补免疫」去做，恰恰是稀释雨天核心、走向四不像的路径。
- `_tcDropOf` 结果：6 只得分几乎并列（41.25/40），选中的替换目标 `dropIsRainCore=true`。**算法愿意丢掉任何一只雨天核心**，因为它没有「这只对体系承重」的概念。

结论：用户的担忧成立。根因是 ① 无队伍级意图锚点；② 缺陷绝对化、不区分性质；③ 换人这种最重的手段与微调同级提供；④ 无体系守护；⑤ 各缺陷独立按钮、无统一目标。

## 2. 设计总览（五个支柱）

### 支柱一：队伍意图锚点 `teamIntentOf(tm)`

纯函数，返回结构化「画框」：

- **theme 主题**：占优天气/场地 + 置信度（雨/晴/沙/雪/电场/草/超场，或 mixed 不强行套框）。
- **stance 姿态**：HO 强攻 / balanced 平衡 / stall 受 / 空间 / 顺风。
- **pace 速度结构**：均速档 + 是否有控速。
- **core 核心成员**：哪些对主题/姿态承重（设置手 + 体系受益者），受保护。

**必须两趟循环**（先汇总每只信号→定主导主题→再标注核心/补位），单趟边算边用会全错。

雨天置信度信号（权重）：降雨设置手、悠游自如/雨盘/湿润之躯等雨专属特性、水本系。明显占优才定主题，否则 mixed。

已确认的自动天气特性名：降雨（雨）/干旱（晴）/扬沙（沙）/降雪（雪）。

### 支柱二：缺陷三级重分类（相对意图，而非绝对）

原始规则条件保留，新增分类器 `_tcClassify(hit, intent)` 把每条映射到：

- **A 内部矛盾·真硬伤（必改，且优先在体系内解决）**：自己的计划无法执行。例：雨队带悠游自如却无降雨手（特性白给）；空间队无慢速受益者；胜负手被全队无法施压的点克制；道具/招式直接互废（讲究锁变化招）。
- **B 可接受的代价（默认不动，不给修复按钮）**：姿态明知要付的。HO/玻璃大炮的脆皮、雨队共通电/草弱点、盾向低攻、很少换人的入场税。明确写「这是 X 姿态的固有代价，不建议为此拆核心」，仅作背景，并注明什么条件下才升级为真问题。
- **C 他法可解（给替代手段，不推荐换将）**：速度先手、免疫/引水/避雷针类队友、控速（顺风/空间/电磁波）、操作（披带/守住/换人节奏）、单槽换招、EV/性格微调。按「最小干预」排序，换将排最后。

### 支柱三：最小改动层级（永远先给最便宜的解法）

1. 打法/操作（零改动：换序、不硬换、保披带、抢速）
2. EV/性格/道具微调（不动成员与招式身份）
3. 单槽换招（保留成员，已有的「换哪招」并入）
4. 补位（队未满或确有冗余槽时）
5. 换人（最后手段）：**不得替换受保护核心**；只能动补位/冗余成员；来将须与主题兼容（对立天气手阻断/靠后）。无安全替换对象时禁用换将并提示走微调。

`_tcDropOf` 改为**约束优化**：先剔除核心成员，再在合格补位中取通用分最高，且校验来将主题兼容。

### 支柱四：体系/身份守护

- 修复不得与主题冲突：来将的天气/场地设置手须与主题一致（雨队不引入干旱/扬沙覆盖雨）。
- 卡顶加**身份行**：「检测到：雨天 · 强攻（HO）｜核心 4 / 补位 2」，所有建议相对该锚点解读。
- 对立体系候选显式标注并靠后（沿用 mate 推荐已有排序），不静默提供。

### 支柱五：一份统一修复计划，取代 N 个独立按钮

- 真硬伤 A（条）：最小修复。
- 可接受代价 B（条）：折叠为背景，无修复。
- 他法可解 C（条）：最便宜干预。
沿用 v4.414 已有的三级折叠卡，重映射其语义，给一个连贯目标，防止顺序漂移。

## 3. 落地拆解（字节级补丁，控制体积）

- **4417a**：`teamIntentOf` + 两趟信号 + 身份行；用多支真实队伍（雨/晴/沙/HO/受/混合）探针验证。
- **4417b**：`_tcClassify` 缺陷三级重分类 + 卡片语义重映射（A/B/C）。
- **4417c**：最小改动层级 + `_tcDropOf` 约束化 + 体系守护。
- 体积：上限余量约 85KB。合并现有内联「怎么修」重复长文、由分类器统一产出，以抵消新增；目标净增长最小。27 个历史保留函数与既有判定口径不动。

## 4. 验收标准（可核对）

- 雨队：电/草弱点由「硬伤」降为 B（可接受代价），身份行正确识别雨天与核心；`_tcDropOf` 不再把核心列为可替换。
- HO 队：脆皮不再被要求改耐久，B 类；真硬伤只保留「计划无法执行」类。
- 混合队：识别为 mixed 时不强行套框，建议保持中性最小。
- 换将路径：核心不可选；对立天气手不可作为来将；无安全对象时禁用。
- 门禁：check_inline_syntax / harness 重建 / smoke 34 / gate offHist 零漂移 / verify_invariants 0 违规。

## 5. 落地结果（4417a/b/c 均已实现并验证）

- **4417a 意图锚点**：`teamIntentOf(tm)` 严格两趟。主题按设置手(+3)/受益特性(+2)/对应本系(+1)打分，对齐成员过半（≥max(2,ceil(n/2))）才定，否则 mixed；天气主题有受益无设置手 → setterGap。姿态只看基础面板（不扫可学招式，避免顺风/空间误触发）：isWall / isOff / 空间(慢速过半且非墙) / 受队(墙≥2) / 强攻(无墙且进攻过半) / 平衡。置信度 /(n*4) 封顶 100。身份行 `teamIntentLineHtml` 挂体检卡 h3 后。七原型验证：雨 100/平衡、晴 88/平衡、沙 79/空间（慢成员触发，已知边界）、雪 96/平衡、HO 21/强攻 core6、受队 17/受队 core6、混合 25/平衡 core4。
- **4417b 缺陷重分类**：注入 `INTENT` 与 `TC_THEME_WK` 主题固有弱点表（雨[电,草]、晴[水,地,岩,冰,毒,虫,飞]、沙[水,草,冰]、雪[岩,钢,火,格斗]）。Rule of Two 全落在固有集合 → B(3)，否则 A(2)；反强化 phaze 强攻姿态 → C(1) 否则 A(2)；天气/场地依赖没答案 → 升级 A(2)；盾位无续航受队 → A(2) 否则 C(1)。`_tcVList` 重写：A 默认全给、B 进独立折叠且无修复按钮、C 提示折叠、参考并入深度。雨队实测：B=弱点超标电×6 草×6，A=phaze，C=8 条，默认「硬伤 1·提示 8」。
- **4417c 最小改动换人约束**：`_tcDropOf` 先取 coreIds 建核心集合，只在非核心成员中跑聚合分；全员皆核心返回 `{drop:null,noSafe:true}`。`tcApplyCand` 增加对立天气体系守护（来将经 `isAbilSet` 检测自动天气，与当前主题不同则 toast 阻断，只拦特性自动天气不拦可学招式）；满队且 noSafe 时 toast 建议走换招/微调并 return，取消「默认换最后一只」兜底。验证：全核心雨队 noSafe；5 雨核心+妙蛙种子正确锁定妙蛙种子为唯一可替换；班基拉斯（扬沙）对雨队识别为对立冲突。
- **已知小瑕疵**：B 条目正文仍保留「分散属性/补免疫」旧措辞，与「可接受」框定略有张力，留待后续文字微调。
